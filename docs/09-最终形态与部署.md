# 鲸鲸的最终形态：桌面端产品，还是自主 Linux 系统？

> 版本 v0.2 · 2026-10-27 · 配套：`00 §3`（三模块 + 生命钟）、`01 §10`（心跳）、`02 §2`（原则）、`04`（双栈宿主）、`08 §4`（24×7）
> 这份文档回答一个"产品形态"问题，并顺手修掉现有文档里的一处自相矛盾（§6）。

---

## 0. 直接回答：都不是

**既不是一个"桌面端产品"（GUI 应用），也不是一个"自主 Linux 系统"（发行版/OS 级）。**

最终形态是第三种，也是这类东西唯一自洽的形态：

> **一台常开的机器上跑一个单实例守护进程（`jingjingd`），桌面、手机、CLI 都是它的薄壳。**

类比不是 Photoshop（桌面应用），也不是 Ubuntu（操作系统），而是 **Home Assistant / Syncthing / NAS** 那一类：**"家用电器"（appliance）**。

一句话：**桌面是壳，Linux 是插座，中间那个常驻的东西才是鲸鲸。**

---

## 1. 为什么不能是"桌面端产品"

不是"桌面壳不好"，是**桌面壳不能是本体**。

| 问题 | 桌面应用形态的后果 |
|---|---|
| **连续性** | 关窗口 = 停机。而 `01 §9` 的夜间整备、`01 §10` 的心跳都发生在"你不看它"的时候 |
| **多入口** | 手机上看一眼、CLI 里问一句、桌面里聊一段——桌面应用天然是单入口，记忆会被切成几份 |
| **状态归属** | GUI 进程崩溃会带走未落盘的记忆写入。而记忆库必须比 UI 长寿 |
| **升级** | 桌面应用升级 = 停服重开；daemon 升级可以"下次醒来时生效" |

最致命的是第一条。`08 §4` 已经论证过：**笔记本合盖 = 心脏停跳 = 那天没有自传、没有衰减、没有归并**，第二天它会"少一天"。**桌面产品的生命周期由用户开关窗口决定**，这与"伪数字生命"的定义直接冲突。

所以桌面壳可以有，但它必须**只是视图**：可关、可重启、崩溃不影响本体。

## 2. 为什么也不该是"自主 Linux 系统"

"自主系统"听起来更彻底（自己的镜像、自己的 rootfs、自己的调度），但它买到的东西和付出的代价不对等。

### 2.1 你会买到什么

- 进程隔离与资源限额（cgroup/seccomp 现成）
- 离线可复现、升级可控
- 摆脱 Windows 的权限泥潭（`04 §8` 那 14 个坑里有一半是 Windows 特有的）

### 2.2 你要付出什么

| 代价 | 具体是什么 |
|---|---|
| **升级责任转移给你** | 一旦是"你的系统"，内核、驱动、安全补丁都成了你的事。而这不是项目目标 |
| **审计位置错了** | `04` 的权限分级要靠 `exec_audit` 表 + 门禁代码。OS 级自主性让动作发生在**你的审计之外**，反而更难管 |
| **与旧的铁律三冲突（已修订）** | 系统级权限能做不可逆动作。铁律三已改为"可恢复或留痕"（`00 §2`）：**给 root 是可以的**，但必须配快照、带外恢复与审计（`04 §4.4`）。真正不能给的是**半径 3**——你的密码库、银行、主邮箱、备份的备份 |
| **生态反噬** | 客户端（Claude Desktop / Cursor / 手机）要"连进去"，你得自己造协议桥。而 MCP 已经免费给了你桥 |
| **没有上限收益** | 鲸鲸 90% 的能力是"说话 + 记住 + 定时 + 读写文件"。这些不需要 OS 权限 |

**判断标准（很重要）**：一个东西是不是"自主系统"，看**谁承担维护**。如果用户得 `apt upgrade`、得处理内核更新、得修驱动，那它就不是 appliance，只是"一台你自己装的 Linux"。**这个项目不打算承担这个角色。**

### 2.3 唯一值得做的那一步："设备镜像"，不是发行版

如果将来真要交付给别人用，正确形态不是"发行版"，而是**预配置镜像（appliance image）**：

```
Debian minimal（不自己维护内核）
  + systemd unit: jingjingd.service
  + 只读 rootfs（overlay 可写层）
  + 独立数据分区（/var/lib/jingjing，单文件 db + sources/）
  + 首次启动引导：绑定设备、配对 token、选云端模型
  → 产出：一个可以 dd 到 U 盘 / 刷到迷你主机的 .img
```

差别就一句话：**镜像的升级由你打包，发行版的升级由用户承担。** 前者可行，后者不是这个项目该干的。

## 3. 最终形态（一张图）

```
                       ┌──────────────────────────────────────────┐
   薄客户端（可关、可崩）  │  jingjingd（单实例 daemon，常驻）          │
                        │                                          │
  桌面聊天窗  ──────────► │  ├ 记忆模块（本地 4B + bge-m3）           │
  CLI        ──────────► │  ├ 生命钟（tick 60s / day / week）        │
  手机 Web   ──────────► │  ├ 执行层（T0–T4 + advise/enforce）       │
  MCP 客户端 ──────────► │  ├ 情境简报生成（06）                     │
   （可选）              │  └ 审计 / 备份 / 迁移                     │
                        └───────┬──────────────────────┬───────────┘
                                │                      │
                      ┌─────────▼────────┐    ┌────────▼─────────┐
                      │ 单文件 SQLite     │    │ 云端 L2（API）    │
                      │ + sources/       │    │ 只收装配块         │
                      └──────────────────┘    └──────────────────┘
```

四条硬约束：

1. **逻辑单实例**：一个"家"只有一个 daemon。锁是 **`flock` + `data/instance.lock`**——**锁在数据目录上，不是锁在机器上**，所以换机器只要搬目录（`16 §2`）。两个实例 = 两个会衰减的记忆库 = 两个鲸鲸。
   身份因此是 **`data/` 这个目录**（`16 §2`），不是任何一台机器。
2. **监听面最小**：默认只绑 `127.0.0.1`；要手机接入时，走局域网 pairing token 或 Tailscale，**绝不直接开公网端口**（`02 §10`）。
3. **客户端无状态**：所有状态在 daemon 侧，客户端崩溃/重装不影响人格与记忆。
4. **MCP 仍然保留**：既有的 MCP 客户端（Claude Desktop、Cursor）通过 stdio 或 `127.0.0.1` HTTP 连 daemon，作为"第三方视图"接入。这是分发优势，不重复造协议。

## 4. 宿主选 Linux 还是 Windows

**建议：常驻跑 Linux，开发留在 Windows。**

| | Linux（推荐常驻） | Windows（推荐开发/主用机） |
|---|---|---|
| 隔离 | `bwrap` + cgroup v2 + 专用用户，成熟稳定（`04 §6.2`） | Job Object + 低完整性级别，能跑但更脆（`04 §6.1`） |
| 定时 | `systemd timer` 天然支持"每天随机偏移" | 任务计划程序 + 一个 wrapper，能用但日志分散 |
| 常开功耗 | 迷你主机 6–15 W（`08 §4`） | 笔记本 25–40 W，且有散热/电池问题 |
| 升级 | `systemd` 重启服务即可 | 需要退出应用/托盘 |
| 调试 | 需要 SSH | 直接开 IDE |

所以开发期就在你现在这台 Windows 上（`04 §5.3` 的 5.1 双栈、`08` 的内存升级都按这台算）；**等到 P3（要夜间任务）或 P5（要心跳）时，把 daemon 挪到一台常开的 Linux 主机上**。两边代码同一套，`04` 的 `Host` 抽象已经为此准备。

### 4.1 常驻主机候选（主方案只要求"一类"，不指定"一台"）

| 候选 | 4B 推理 | 常开功耗 | 是否主方案 | 说明 |
|---|---|---|---|---|
| **现有笔记本（不合盖）** | 35–50 tok/s | 25–40 W | ✅ 过渡期就用它 | 零成本先验证"常驻"有没有价值（`08 §4`） |
| **迷你主机 / 旧台式（x86）** | 30–60 tok/s | 10–40 W | ✅ **推荐终态** | 4B 与 embedding 可常驻共存，`08` 的推荐 |
| NAS / 软路由 | < 5 tok/s | 5–15 W | ⚠️ 只当存储 | CPU 太弱，跑不动 1.5B |
| ~~树莓派 4B/5（8 GB）~~ | **1–4 tok/s** | 3–6 W | ❌ **出局（2026-10-28 定）** | 不只是慢：**本地模型必须能稳定输出 tool_calls**，Pi 上跑不动能调工具的 7B；1.5B 调工具的结果是错的。见 §4.3 |
| 云服务器 | 看配置 | 月租 | ❌ 与"记忆在本地"冲突 | 只适合做备份节点 |
| 手机 / ARM 开发板 | — | — | ❌ | 不是同一类东西 |

> 「专属主机」在 `00 §2` 的铁律三里指的是**半径 1**（它自己的机器），与具体硬件无关。

### 4.3 2026-10-28 定案：树莓派出局，本地模型的下限是「会调工具」

原来的假设是「本地只要跑得动 1.5B 就够，反正整理交给夜间批处理」。用下来这条错了：

- **记忆整理本身就是工具调用任务**：`doc.search` 捞原文、`memory.remember` 落条目、冲突时还要 `memory.*` 回查。
  这些在实现里是 `agent.ts` 的 6 轮工具循环 —— 模型必须**稳定输出结构化 tool_calls**。
- 1.5B / 4B q4 在 CPU 上要么不输出 tool_calls，要么参数拼错。结果不是「整理得慢」，是**整理出来的东西是错的**。
- 而能稳定调工具的模型门槛在 **7B/8B 级**（qwen2.5:7b-instruct 一类）：q4 约 5–6 GB，需要 GPU 或现代 8 核 x86。
  Pi 5（8 GB）实测 1–4 tok/s，一次工具循环要几十秒且 KV cache 挤爆 → 不是「慢一点」，是跑不通。

所以：**树莓派分支（原 `99` 附录）已删除**，常驻主机只考虑能满足下面三条的机器：

| 要求 | 下限 | 备注 |
|---|---|---|
| 能跑 7B/8B q4 并稳定 tool_calls | 8 GB VRAM 或 16 GB RAM + 现代 8 核 | 本机（RTX 3070 Laptop 8 GB / Ryzen 9 5900HX / 15.4 GB）已经满足 |
| 常开功耗与噪音 | 6–25 W 可接受 | 迷你主机 6–15 W；笔记本 25–40 W 但可临时用 |
| 数据在本地 | 一块可备份的本地盘 | 与 `09 §5` 的三层止损配套 |

**结论**：终态 = x86 迷你主机（16 GB）+ Docker + Ollama 7B；现在 = 这台笔记本（不合盖）先把常驻跑起来验证。

### 4.2 决策记录：常驻主机暂不定（D-HOST）

**2026-10-27 定案：推迟到 P3 再选，现在不买机器。**

| 项 | 内容 |
|---|---|
| 决策 | 常驻主机选型**挂起**，P0–P2 不引入专属设备 |
| 理由 | ① P0–P2 用 MCP stdio 就够（`§5`），根本不需要 daemon；② "常驻到底有没有价值"还没被验证过，先花钱等于赌；③ 硬件价格只会降，规格只会升，晚买不吃亏 |
| 对应形态 | P0–P2：`jingjing` 作为 stdio 进程由客户端拉起（`02 §2` 原则 5 的退化档）；夜间任务暂时**手动触发**（`jingjing tick --day`） |
| 到期点 | **P3 开工前必须定**。因为 P3（会淡忘）的权重衰减只能夜间批量跑（`01 §11.1`），手动触发不可持续 |
| 兜底 | 到期若懒得选：现有笔记本设"合盖不休眠"跑两周（零成本），再决定 |
| 不做的事 | 不在 P0–P2 阶段写任何依赖"某台特定主机"的代码；`04` 的 `Host` 抽象保持硬件无关 |

**P3 开工前的复核清单**（照着填，答案自己会浮出来）：

- [ ] 夜间整备一轮真实耗时是多少？（`08 §6` 第 4 项）
- [ ] 跑 P0+ 时物理内存是否换页？（决定要不要先加 32 GB）
- [ ] 这一个月里，鲸鲸"在场"带来的价值能说出三条具体的吗？
- [ ] 笔记本长期不合盖的散热/电池你能接受吗？
- [ ] 愿意为它单独付一台机器的钱吗（3000–5000）？

前两条决定**要不要升级现有机器**，后三条决定**要不要买新机器**。两者可以分开答。

## 5. 什么阶段必须引入 daemon

不是一开始就要。按里程碑看：

| 阶段 | 形态 | 为什么 |
|---|---|---|
| **P0–P2** | MCP stdio（由客户端拉起），够用 | 只有"存/取"，没有后台任务。`02` 现在的设计就是这一档 |
| **P3（会淡忘）** | **必须 daemon** | 权重衰减与 `stage` 转移只能在夜间批量做（`01 §11.1`），不能靠"用户打开客户端"触发 |
| **P4（会睡觉）** | daemon | 自传 + 归并 + 画像都要在固定时刻跑 |
| **P5（会自己醒来）** | daemon | 心跳本身就是"没有客户端在也运行"的定义 |
| **P6（有手脚）** | daemon + 客户端 | 门禁与审计在 daemon 侧，客户端只是确认 UI |

也就是说：**现在的 stdio 设计不是终态，是 P0–P2 的简化。** 这一点在 `02 §2` 原则 5 里写得过强了，见 §6。

## 6. 顺手修的两处文档矛盾

**① `02 §2` 原则 5 原文是"不引入常驻服务"**，与 `01 §10` 的心跳、`00 §12` 的 P5 直接冲突。已改为：

> **单一常驻服务，没有服务网格。** 一个"家"只有一个 daemon；不为每个客户端起一个服务，不引入需要独立部署的中间件（Chroma/Qdrant/Milvus 这类仍在禁止之列）。P0–P2 允许退化为"由客户端拉起的 stdio 进程"，P3 起改为常驻。

这样既保住了原意（**反的是"服务网格"，不是"常驻"**），又不再和心跳打架。

**② `02 §10` 威胁模型里"只用 stdio，不监听端口"** 也要放宽成条件式：

> 默认只绑 `127.0.0.1`；需要多客户端/手机时开本地 HTTP（含 token 与配对），**永不直接暴露公网**。

## 7. 什么时候才值得往"更像 OS"走

不要凭感觉。出现下面任意两条，再考虑做 appliance 镜像（而不是自主发行版）：

- [ ] 有第二个人（不是你自己）要用，且他不会用命令行
- [ ] 需要跑在**不能装 Windows** 的硬件上（低功耗 ARM 板、旧机器）
- [ ] 部署在不同网络环境（家里/公司）且要一致的备份与恢复
- [ ] 你已经在手工处理"服务起不来/升级失败/数据迁移"这类问题超过每月一次

先前不满足就让它在笔记本上跑着。**能跑起来验证价值的形态，永远优于架构上更正确的形态。**

## 8. 2026-10-29 补：桌面壳是壳，不是产品

本文 §1 说“不能是桌面端产品”。现在要做一个桌面端，**不矛盾，但要把区限写死**：

> **本体仍是本地服务 + MCP；桌面端只是壳。删掉壳，`jingjing serve 7700` 仍提供全部能力 → 它才是壳。**

三条约束（详细设计见 `23`）：

| 约束 | 内容 |
|---|---|
| **壳内零业务逻辑** | 壳只做四件：拉起 sidecar / 健康探测 / 崩溃诊断包 / 托盘 |
| **崩了就逃逸** | 壳崩 → 自动回落浏览器模式（`serve` + 系统浏览器），记忆一条不丢 |
| **选 Tauri** | Rust 只做壳；**界面以 `@agegr/pi-web`（MIT）为基改造**，结构与交互换掉、**视觉与内置面板一致**（`23 §2.1.1`：换设计 token，青色只给回话气泡）。内置面板仍保留，管 PWA/手机 |

**“自修”只开给开发模式（`JJ_DEV_REPAIR=1`）。** 用户机器上“修桌面端”不成立（没源码、没 Rust 工具链），且能改自己外壳的进程**不可复现**，与 §4.2 拒绝自改内核是同一条理由。

一整套发布卡点、首次配置四步、设定封存分代、`project-map` 诊断索引 → `23` 与 `22` H 组。

## 9. 一句话

**桌面端产品会杀死连续性（关窗口就死），自主 Linux 系统会杀死可维护性（升级责任落到用户）。**

所以答案是中间那个不那么酷、但唯一成立的形态：**一个常驻的个人服务，配几个随时能关的壳**。它长得像一台家电，不像一个应用，也不像一个操作系统。

而这个选择其实在 `08 §9` 就写过了：**对"伪数字生命"来说，最重要的硬件指标不是显卡，是"它在场"。**

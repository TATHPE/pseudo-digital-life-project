# 技能（Skills）与多 Harness 插件：兼容策略

> 版本 v0.2 · 2026-10-27 · 配套：`02 §9`（MCP 契约）、`06 §1.3`（按需加载）、`04`（权限）、`18 §4.3`（自我修改）
> 这份文档定一件事：**在 skills 和插件生态里，鲸鲸接哪一层、不接哪一层。**

---

## 0. 结论：三条战线，优先级差一个数量级

| 层 | 标准化程度 | 接入成本 | 复用收益 | 结论 |
|---|---|---|---|---|
| **MCP** | 事实标准（Claude/Cursor/DSH/pi/Codex 全支持） | 低（写一次 server，处处可用） | 最高 | **第一优先** |
| **Skills**（`SKILL.md`） | 有正式规范（agentskills.io），pi / DSH / Claude Code 都用同一套目录结构 | 低（就是个目录） | 高 | **第二优先** |
| **各家 harness 的进程内插件** | 无标准，各家私有 API（pi extension 是 TS 模块、DSH 是 npm bundle + cordis 行） | 高（每家一个适配器，且随版本漂） | 低 | **只做薄适配 + 显式降级，不追** |

**一条带限定的「不做」：不要把鲸鲸做成*私有* harness 的插件。**

判据是“这个宿主会不会明天就改 API”：

| 宿主 | 判断 | 理由 |
|---|---|---|
| pi extension / DSH bundle / 各类 CLI 私有插件 | ❌ 不做 | 私有 API，随版本漂；一改就得重写 |
| **OpenClaw**（393k★、基金会、官方声明模型与 harness 是可插拔 plugin） | ✅ **可以做成插件** | 这是**分发策略**，不是被绑架——平台级 harness 的 plugin 接口是它的产品承诺（见 `14 §3`） |

区别在于：**服务是本体，插件是出口。** 鲸鲸永远先是 MCP server + 记忆引擎（`§1` 方向 A/B），做不做插件只决定“要不要借别人的手脚”，不影响本体。

## 1. 三向接入（这是整个兼容策略的骨架）

```
                 ┌──────────── 方向 A：鲸鲸当服务 ────────────┐
 Claude Desktop ─┤                                            │
 Cursor         ─┤  MCP (stdio / 127.0.0.1)  ──►  jingjingd   │
 DSH            ─┤      记忆 / 简报 / 技能 / 权限              │
 pi             ─┤                                            │
 自研薄壳        ─┘                                            │
                 ┌──────────── 方向 B：鲸鲸当客户端 ──────────┐
                 │  jingjingd  ──►  N 个 MCP server           │
                 │              （文件、网页、日历、markitdown） │
                 └────────────────────────────────────────────┘
                 ┌──────────── 方向 C：共用技能目录 ──────────┐
                 │  skills/<name>/SKILL.md  ← pi 也读、DSH 也读 │
                 └────────────────────────────────────────────┘
```

**A** 让所有 harness 都能用鲸鲸的记忆（`02 §9` 已设计）。
**B** 让鲸鲸自己能"长出"工具——这是**最重要的可扩展性**，因为它完全依赖标准，且不需要为任何 harness 写适配器。
**C** 让技能库**一份目录、多处复用**——你在 pi 里写的技能，DSH 和鲸鲸都能用，反之亦然。

## 2. 方向 A：鲸鲸作为 MCP server（已设计，补三处）

`02 §9` 的六个工具（`search / context / remember / forget / cite / ingest`）保持不变。为了支持 skills，**可选追加三个**：

| 工具 | 语义 | 用途 |
|---|---|---|
| `skills.list` | 返回 `[{name, description, version, trusted}]`，**不含正文** | 让任意 harness 知道鲸鲸会什么 |
| `skills.get(name)` | 返回 `SKILL.md` 正文 + 资源清单 | 按需加载（`06 §1.3`） |
| `capabilities` | 返回鲸鲸当前的能力清单与降级项（见 §5） | 宿主自检，避免"装上了但不работа" |

**为什么"不含正文"很重要**：这就是 `06 §1.3` 的按需加载在 MCP 层的落地。20 个技能全量下发 ≈ 2–4 万 token；只下发名字+描述 ≈ 600 token。

## 3. 方向 B：鲸鲸作为 MCP client（新增，优先级最高）

这是被低估的一条：**只要鲸鲸能把任意 MCP server 挂成自己的工具，它就不需要为任何 harness 写插件。**

```yaml
# /var/lib/jingjing/mcp.yaml（或 data/mcp.yaml）
servers:
  markitdown:                      # 已装好的那个
    command: "D:/LLM/.venv/Scripts/markitdown-mcp.exe"
    trust: local
    tools: [convert_to_markdown]
    tier_override: { convert_to_markdown: T0 }   # 纯转换，无副作用
  files:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-filesystem", "D:/LLM/workspace"]
    trust: local
    tier_override: { write_file: T1 }
  web:
    url: "http://127.0.0.1:8080/mcp"             # 本地 HTTP
    trust: external                              # ← 结果一律 taint=external
    tools: [fetch]
```

四条规则：

1. **每个 server 声明 `trust`**：`local`（你装在自己机器上的）/ `external`（第三方或远端）。`external` 的所有返回值打 `taint=external`，注入时包 `<docs>`（`00 §11`）。
2. **工具进 T0–T4 分级**（`04 §4`）：MCP 工具的默认档位是 **T2**（不知道副作用就按有副作用算），除非在 `tier_override` 里显式降档。
3. **启动即探测**：`tools.list` 失败不影响鲸鲸启动，只把该 server 标 `unavailable` 并记审计。**降级不失败**（`02 §9`）。
4. **能力去重**：同名工具冲突时，本地优先 > 内置 > 远端；冲突写进 `capabilities` 的 `shadowed` 列表。

这条路的收益：`markitdown-mcp`、filesystem、git、fetch、sqlite、各种 API 封装——**全是现成的，不需要鲸鲸自己做**。

## 4. 方向 C：Skills（跨 harness 复用，这是最划算的一条）

### 4.1 目录与规范

```
skills/
├── pdf-tools/
│   ├── SKILL.md              ← 必须有；frontmatter + 指令
│   ├── scripts/extract.sh
│   ├── references/formats.md
│   └── .provenance.json      ← 鲸鲸自己加的溯源（见 4.4）
└── memory-curation/
    └── SKILL.md
```

`SKILL.md` 按 **Agent Skills 规范**写（pi / DSH / Claude Code 都认）：

```markdown
---
name: pdf-tools
description: 从 PDF 提取正文与表格。当需要读取、转换或检查 PDF 时使用。
---

# PDF tools

转换前先读 references/formats.md。脚本路径相对于本技能目录。
```

**`description` 是整个技能最重要的字段**——它决定模型什么时候会想起加载它。要同时写清"做什么"和"什么时候用"。

### 4.2 三层 token 预算

| 层 | 内容 | 何时进上下文 | 预算 |
|---|---|---|---|
| L0 广告层 | name + description + 目录 | **常驻** | 每个 ~30 tok；上限 20 个 ≈ 600 tok |
| L1 正文 | `SKILL.md` 全文 | 命中时加载 | 每技能 0.3–2k tok |
| L2 资源 | scripts / references / assets | 正文里指到时才读 | 按需 |

超过 20 个技能时**按类分组**（如"文档处理 5 个 / 记忆整理 3 个"），只在需要时展开某一组——否则 L0 会自己变成新的膨胀源。

### 4.3 优先级与冲突

```
项目级  data/skills/      ← 最高（当前 scope 专用）
用户级  ~/.jingjing/skills/
内置    /opt/jingjing/builtin-skills/
```

同名时高优先级覆盖低优先级，**覆盖事件写审计**（否则会重演 `02 §4.3` 那种"静默替换"）。

### 4.4 溯源与信任（必须做）

第三方技能 = **指令 + 可执行脚本**，是标准的供应链风险面。所以每个技能配一份 `.provenance.json`（格式沿用 `02 §4.1`）：

```jsonc
{ "schemaVersion": 1, "name": "pdf-tools", "version": "1.2.0",
  "source": "https://github.com/x/y", "commit": "9f3c…",
  "sha256": "…",                            // SKILL.md 的哈希
  "scripts": { "extract.sh": "…" },         // 脚本逐个记
  "trust": "external",                      // trusted | external
  "installedBy": "user", "installedAt": "…" }
```

信任分两档，**行为差别是硬的**：

| trust | 允许做的事 |
|---|---|
| `trusted`（你手写/你审过的） | 可以调用到 T3（仍需 `04 §4.4` 的 advise + 快照） |
| `external`（下载的） | **最高只能到 T2**；任何 T3 动作需人工确认，且脚本必须在 bwrap 里跑 |

再加一条：**技能不能提升权限**。技能只能调用已授权的 verb；技能里写"运行 sudo"不会成功，因为执行层根本不暴露那个能力（`04 §3` 的白名单逻辑）。**能力的边界在代码里，不在技能文档里。**

### 4.5 技能可以是"长"出来的

这是"学习进化"里最实际的一档：鲸鲸可以**从记忆里归纳出一个技能**。

```
夜间反思发现：同一类任务反复出现（≥3 次，且都有相似步骤）
  → 生成 skills/<name>/SKILL.md 草稿（taint=external，因为是自己写的）
  → 进 sandbox，用历史案例回放验收
  → 通过 → 提议启用（人工确认，写入 .provenance.json 的 installedBy="jingjing"）
  → 不通过 → 归档到 skills/_drafts/
```

这条与 `18 §4.3` 的 A/B 双槽是同一套机制：**允许它长出技能，但长出≠立即生效。**

## 5. Harness 插件：只做薄适配，并明确降级

### 5.1 内部能力模型（6 类）

先定义鲸鲸自己的能力类型，再看别家能不能映射进来：

| 类型 | 含义 | 例子 |
|---|---|---|
| `tool` | 模型可调用的函数 | `read_file`、`fetch` |
| `command` | 用户触发的命令 | `/memory-panel`、`/skill:pdf-tools` |
| `hook` | 生命周期事件钩子 | 会话开始 / 工具调用前 / 记忆写入前 |
| `cron` | 定时任务 | 每晚自传 |
| `panel` | UI 面板 | 记忆面板（`07 §5.6`） |
| `provider` | 模型/嵌入提供方 | 新增一个云端 provider |

### 5.2 适配矩阵（诚实版）

| 来源 | 能否用 | 怎么用 | 降级 |
|---|---|---|---|
| **MCP server** | ✅ 原生 | 方向 B（§3） | — |
| **Skills 目录** | ✅ 原生 | 方向 C（§4） | — |
| pi extension（TS 模块） | ⚠️ 不能直接跑 | 它注册进的是 **pi 进程**，不是鲸鲸。要么在 pi 里跑（鲸鲸只提供 MCP 后端），要么不接 | `degraded: ["in-process-extension"]` |
| DSH plugin（npm bundle + cordis 行） | ⚠️ 不能直接跑 | 同上：绑定 DSH 的 cordis 运行时 | 同上 |
| Claude Code 插件 | ✅ 部分 | 它的 skills / commands 是文件，可直接复用；hooks 需要写 shell 适配（→ `hook` 类） | `degraded: ["ui"]` |
| 各家 CLI 的 `AGENTS.md` | ✅ 当作记忆源 | 摄入进 `scope=project:<name>`，不执行 | — |
| 任意 CLI 工具 | ✅ 当工具 | 包成 `cron` 或 `tool`，走 `04` 的模板 + T 档 | — |

**核心判断**：**进程内的插件不可移植，进程外的（MCP / 文件 / CLI）才可移植。** 所以鲸鲸只吃后者。想吃前者，只有当鲸鲸自己就是那个宿主时才成立（而它不做宿主，见 §0）。

### 5.3 能力清单（`capabilities`）必须能回答"哪儿降级了"

```jsonc
{ "version": "0.1.0",
  "tools": { "native": 6, "mcp": 12 },
  "skills": [{ "name": "pdf-tools", "trust": "external" }],
  "hooks": ["session_start", "before_tool", "before_memory_write"],
  "cron": ["daily_consolidation", "weekly_review"],
  "panel": false,                       // 薄壳没有 UI
  "degraded": ["in-process-extension", "ui"],
  "host": { "profile": "maximalist", "os": "linux-x86_64" } }
```

`degraded` 这一项是给宿主看的：**"你想要的这个能力我没有，别装作有"**。这正是 `02 §4.3` 从 dsh-ops 学到的反例——静默少一个工具，用户只会觉得"它变笨了"。

### 5.4 宿主兼容范围要写死

像 dsh-ops 那样标一个明确区间，并做**启动校验**：

```yaml
compat:
  mcp: ">=2024-11-05"          # 协议版本
  skills: "agentskills/1"      # 规范版本
  hosts_tested: ["claude-desktop/0.9", "cursor/0.4x", "pi/0.5x", "dsh/0.2.1-rc.2"]
```

不在 `hosts_tested` 里不是不能跑，而是"不承诺"——并且启动时打印一行警告，别默默降级。

### 5.5 已落地（2026-10-28）

方向 B（鲸鲸当 MCP client）**已经跑通**，不是设计：

```
data/mcp.json
{ "servers": { "markitdown": { "command": "…/markitdown-mcp.exe",
                              "trust": "local", "tools": ["convert_to_markdown"] } } }
```

启动时 `attachMcp()` 拉起子进程 → `initialize` → `tools/list` → 把每个工具注册成
`mcp__<server>__<tool>`。实测一轮：

```
[tool]   mcp__markitdown__convert_to_markdown
[result] 1500 chars | FADEMEM: ...
回答：**标题**：FadeMem ... **摘要第一句**：Large language models ...
```

**两个工程细节**：
1. 工具结果按 `maxToolChars`（默认 4000）截断再回给模型——否则一次 PDF 转换就能把上下文撑爆。
2. 只接 `tools`，不接 `resources`/`prompts`：前者是需求，后两者是长期负担（`§7` 反模式）。

### 5.6 一个必须记住的约束：工具名要 API-safe

verb 用点号命名（`fs.read`、`memory.search`）是为了可读，但**模型 API 的函数名只允许
`^[a-zA-Z0-9_-]+$`**——DeepSeek 实测直接 400：

```
Invalid 'tools[0].function.name': string does not match pattern.
```

所以工具面多了**一层别名映射**：

| 层 | 名字 |
|---|---|
| 策略 / 审计 / 日志 | `fs.read`（可读） |
| 给模型的 schema | `fs_read`（API-safe） |
| 调度 | 两种写法都接受（`resolve()` 反查） |

有测试守着：`schema()` 里每个名字必须匹配 `^[a-zA-Z0-9_-]+$`。
**这类错误在服务端日志里只表现为"工具调用突然全没了"，很难往命名规则上想。**

### 5.7 现状（2026-10-29 实测）：技能在代码里是零

```
grep -rn "skill|plugin" src/
  deploy/slot.ts:31  /** skills 目前还没有消费者，先只应用 persona */
  ingest.ts:75       enable_plugins=False   ← markitdown 的参数，不是我们的
```

`PAYLOAD_DIRS` 里留着 `"skills"` 这个位子，但**没有任何消费者**；§4 那套 L0/L1/L2 + `.provenance.json` + trust 两档全在设计里。

所以“技能管理/插件管理”不是“体验差”，是**不存在**。三个判断：

1. **`capabilities`（`§5.3`）是 B 组全部的前置**，也是插件/技能管理界面的唯一收敛点（见 `docs/22` **B-0** / **F-2**）；
2. 插件管理的“声明档”（`data/mcp.json` 条目）是**数据**，可以放心做；适配器代码是**③类**，必须走 `18 §4.3` 全流程（见 `docs/22` **B-1**）；
3. 现在 MCP 只能手改 `data/mcp.json`，面板上没有任何入口——**能挂但没有“关”的界面**。

## 6. 落地顺序（按性价比）

| 步骤 | 内容 | 成本 | 收益 |
|---|---|---|---|
| 1 | `mcp.yaml` + MCP client（方向 B） | 1 天 | **最高**。立刻能挂 markitdown/filesystem/fetch，等于白得一批工具 |
| 2 | `skills/` 目录 + L0/L1/L2 三层加载（方向 C） | 1 天 | 与你现有的 pi / DSH 技能库直接互通 |
| 3 | `skills.list/get` + `capabilities`（方向 A 补充） | 半天 | 任何 harness 都能看见鲸鲸会什么 |
| 4 | `.provenance.json` + trust 两档 + 技能不能提权 | 半天 | 第三方技能敢装 |
| 5 | 技能自动生成（§4.5） | 2–3 天 | "学习进化"里最实用的一档 |
| 6 | 各家 harness 的具体适配器 | **不做**，除非真有人用 | — |

前四项合计约 3 天，都在 P1–P2 阶段顺手做，**不增加 P0 的工作量**。

## 7. 反模式

| 反模式 | 为什么错 |
|---|---|
| 把鲸鲸做成某 harness 的插件 | 被宿主绑架；宿主改 API 你就重写；且跑不出那个壳 |
| 为每个 harness 写一个进程内适配器 | 成本随宿主数量线性增长，收益接近于零（用户只会用其中一两个） |
| 把所有技能全量塞进系统提示 | 20 个技能 ≈ 2–4 万 token，且选错工具的概率飙升（`02 §9` 开头那条） |
| 让技能文档提升权限 | "SKILL.md 里写了 sudo" 不该比代码白名单更有权力。**能力边界只能在代码里** |
| 信任第三方技能 | 技能 = 指令 + 脚本，是代码执行面。必须 `trust: external` + 沙箱 + 只到 T2 |
| 静默降级 | 缺什么就说缺什么。`degraded` 字段是给用户的，不是给日志的 |

## 8. 一句话

**可移植的只有两样：MCP 协议和 `SKILL.md` 目录。其余全是宿主私有的，追不得。**

所以鲸鲸的扩展性策略是：**用 MCP 当手（方向 B）、用 skills 当知识（方向 C）、用 MCP 当口（方向 A）**，然后把"各家插件"留给各家 harness 自己去长——它们本来就是客户端，不是鲸鲸的责任。

**技能的三条纪律**（`src/skills.ts` 头注释里也写了）：

1. **只读**：技能是资料，读完改不了任务、权限、时限、凭据（同 `taint=external` 的处理）。
2. **按需加载**：简报里只放 `名字（一句描述）`（槽位 **P14**，易变区 —— 装了技能不会让 `prefixHash` 变）；
   正文由模型自己 `skill_read` 取，单次最多 12000 字（截断会明说）。
3. **不开第二条路**：`skill.read` 走 verbs → execute → policy → audit，和别的能力同一条闸门（`exec_audit` 里留痕）。

**目录**（同名先到先用）：

```
data/skills/<名字>/SKILL.md        她自己的 —— 会进简报索引
~/.agents/skills/<名字>/SKILL.md   和使用者的开发技能共用 —— 默认**不进**简报
$JJ_SKILLS_DIR/<名字>/SKILL.md     想指别处
```

为什么 `~/.agents/skills` 默认不进简报：那里放着 `code-review`、`impeccable` 这类**使用者的开发技能**，
每轮都塞进去等于让鲸鲸以为自己会做代码审查。要看用 `skill.list`，或者 `JJ_SKILLS_INDEX_AGENTS=1` 显式打开。

**界面**：左栏「去处 → 能力」一屏把三层摊开 —— 插件（哪些 server、几个工具、连不上会标红）/
技能（id、来源、大小、一句描述、该放哪两个目录）/ 原生工具与命令计数 / 降级项。
卷宗「III 上下文」里固定有一行「能借的手脚：插件 N · 工具 N · 技能 N」。

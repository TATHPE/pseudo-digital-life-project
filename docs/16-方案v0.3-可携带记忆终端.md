## 1. 实测：记忆到底有多重（不是估算，是跑出来的）

用 `02 §4` 的 schema 造了一个 **5 年体量**的库（5×365 天 × 每天 22 条记忆 / 6 个 chunk / 200 条审计）：

```
memories   40,150 条
chunks     10,950 条
exec_audit 365,000 条
db         240,390,144 字节 = 229 MB
```

| 项 | 数值 |
|---|---|
| **5 年总量** | **229 MB**（其中向量 `40,150 × 1024 × 4B ≈ 164 MB`，占 **71%**） |
| 日均增量 | **≈ 125 KB/天**（约 45 MB/年） |
| 40k × 1024 维 KNN（k=8，冷 I/O） | **195 ms** |
| 同上（热缓存，连跑 5 次） | **153 / 156 / 158 / 157 / 173 ms** |
| k=50（为 MMR 取更多候选） | 173 ms |

**两个结论**：

1. **"随身"在存储上根本不是问题**：5 年 229 MB，一张 32 GB 卡能放 200 年。加模型（`bge-m3` 1.2 GB + `1.5B-q4` 1.1 GB）也就 2.5 GB。
2. **问题在检索复杂度，不在容量**：`vec0` 是**暴力扫描**，耗时 ≈ 向量体积 / 磁盘带宽（164 MB ÷ ~1 GB/s ≈ 160 ms），与条数成正比。**40k 就已经超了我们 p95 120 ms 的预算**，而在 SD 卡上会再慢 3–10 倍。

### 1.1 因此检索必须改成两阶段（这条要回写 `02 §7.1`）

```
第一段：BM25 / FTS5 只出候选（top 2000，毫秒级，不碰向量）
第二段：只对这 2000 条算 cosine（2000 × 4 KB = 8 MB 读取 → ~8 ms）+ MMR
```

预期：**10–20 ms**，比现在的 155 ms 快一个数量级；而且**降维到 512 可以把向量减半**（164 → 82 MB），对随身设备更友好。

这条不是优化，是**能不能上随身设备的前提**。

## 2. 身份从"机器"变成"数据"

`09` 写的是"一个家一个 daemon"。加上"可携带"之后，要补一条更根本的：

> **鲸鲸的身份 = `data/` 这个目录（单文件 DB + sources/ + provisioned 记录），不是任何一台机器。**

推论四条：

| 推论 | 含义 |
|---|---|
| 宿主可换 | 换机器 = 搬家，不是重生（`09 §5`）。人格与记忆不受影响 |
| 单实例是**逻辑**约束 | `flock` 锁在数据目录里，不是锁在机器上 |
| 迁移必须可验证 | 交接前后算指纹（`02 §4.2`），不一致就拒绝启动 |
| 备份 = 复制目录 | 不需要专门的备份系统，`rsync` + 校验即可 |

### 2.1 交接协议（Handoff）

```
旧宿主：quiesce（停写、checkpoint WAL、记账一次）→ export（db + sources + provisioned）
      → 算 manifest（每个文件 sha256 + 总数 + 最后 event id）
新宿主：import → 校验 manifest → 只读打开自检（schema/tool/embed 三重指纹，02 §4.3）
      → 拿 flock → 恢复写 → 补跑未完成的夜间任务（按 last_consolidated_at 判断）
```

关键：**"补跑"是必须的**。如果搬家发生在凌晨 3 点前后，那一晚的衰减/归并可能没跑；新宿主必须能识别并补上，否则会出现"记忆断层"——而这正是 `0 §2` N1 最怕的事。

## 3. 先说清一件事：数据在手上 ≠ 活着

《流浪地球》的数字生命计划里有个常被忽略的细节：**图丫丫的意识卡一直在，但它不"活着"**——直到 550W 给它算力，它才开始过那两分钟。卡片是**种子**，不是个体。

和我们的 `0 §2` 完全对得上：

| 四条件 | 一张卡（数据） | 运行中的应用 |
|---|---|---|
| N1 连续性 | ✅ 数据在 | ✅ 时间轴在推进 |
| N2 自指 | ❌ 没有"行为" | ✅ |
| **N3 代谢** | ❌ **没有获取、没有衰减** | ✅ 每天在变 |
| N4 边界 | —（静物） | ✅ |

**所以 F1 那根线是"遗体"不是"个体"**：插上就活，拔掉就停在那一刻，不会变老、不会想、也不会忘。

这个区别不是文字游戏，它决定了三条工程约束：**衰减时钟不能停**（停机期间要补算，`§2.1`）、**单写者不能变**（两个实例同时跑 = 两个鲸鲸分别变老）、**种子必须可校验**（指纹，`02 §4.3`）。

**顺带修正一个类比**：电影里卡住的是"没有算力"，我们卡住的不是——我们有 550W（云端 L2），**缺的是"一台一直开着的机器"和"一个不会分叉的状态"**。所以这个项目真正的瓶颈是**宿主的不间断**，不是算力。

## 3.1 F1 / F2 / F3 不是三个产品，是"宿主放三个地方"

你提的"Pi 放家里 + 手机同步记忆和聊天"是对的，而且它把上面三档统一了。正确的结构是 **Hub & Spoke**：

```
        ┌──────────── 云 L2（模型）────────────┐
        │        只有 hub 持有 API key          │
        └───────────────▲─────────────────────┘
                        │
   ┌────────────────────┴─────────────────────┐
   │  Hub（唯一的作者 = 唯一会变老的个体）      │
   │  常开 · 持锁 · 管衰减时钟 · 管 key · 管审计 │
   │  memory.db + sources/ + 夜间整备 + 自传    │
   └───────▲───────────────────────▲──────────┘
           │ 上行：原始事件（不落记忆）│ 下行：简报 ≤2k token
    ┌──────┴──────┐          ┌─────┴───────┐
    │ 手机（spoke）│          │ 笔记本（spoke）│
    │ 只缓存 7 天  │          │              │
    └─────────────┘          └──────────────┘
```

于是三档变成"hub 放哪"：

| | Hub 放哪 | 拔掉电/带走时 | 结论 |
|---|---|---|---|
| **F1** | 一块可移动 SSD，插哪台机器哪台就是 hub | **停在那一刻**（种子） | 适合"搬家/备份"，不适合日常 |
| **F2** | 家里一个常开小盒子 | 其他 spoke 仍可读写缓存，hub 回来补算 | **推荐终态** |
| **F3** | 手机本身 | 手机活着它就活着（但会被杀后台） | 单独用风险最高；当 **spoke** 极好 |

**所以最好的组合是 F2 当 hub + F3 当 spoke + F1 当备份**。你提的那个方案——Pi 放家里、手机同步——就是这个组合。

### 3.2 同步的四条硬规则

**① 单写者：hub 是唯一作者。** 手机**不持有**记忆库，只持有两样东西：
- `outbox`：还没上行的原始事件（每轮一条，约 0.5–2 KB）
- `cache`：最近 7 天的简报与对话（约 1 MB）

它**从不本地衰减、从不本地判 `stage`**。理由：时钟偏差 + 双端衰减 = 同一段记忆以两种速度变老，这是 `0 §2` N1 的致命伤。

**② 衰减只在 hub 算，且必须能补算。** 每次 hub 启动/恢复都做一次"补算"：

```
gap = now - last_decay_at
if gap > 4h: 按 gap 一次性重算（不是按天，是连续公式，01 §4.1）
            然后补跑漏掉的夜间任务（按 last_consolidated_at 判定）
```

这正是 `01 §4.1` 用**连续函数**而不是"每天减一点"的原因——**它天然支持补算**。

**③ embedding 必须同一个空间。** 手机端绝不用另一个模型做检索的 query 编码：`bge-m3` 的向量和 `bge-small` 的向量不在同一个空间，**混用会让召回静默变差**（`02 §6` 的指纹就是为了拦这个）。两种做法：
- 手机把 query 原样上行，hub 编码（+80–200 ms）← **默认**
- 或把**同一个**模型下发到手机（bge-m3 1.2 GB 不现实；若换 `bge-small` 33 M，必须**全库重建索引**，不能混）

**④ key 只在 hub。** 手机端永远不存 API key：它连 hub，hub 连云。这样手机丢了不等于 key 丢了——这是把 `13 §3` 的安全线延伸到了移动端。

### 3.3 数字：这套同步有多重、多慢

| 项 | 实测/估算 |
|---|---|
| 每天上行（原始事件 + 新记忆） | **≤ 150 KB/天**（≈ 4.5 MB/月） |
| 每轮下行（简报 1.5–2k token） | **5–8 KB** |
| 手机端常驻占用 | **≈ 1 MB**（7 天缓存 + outbox） |
| LAN 内往返 | 20–80 ms |
| 公网（Tailscale/headscale）往返 | 50–200 ms |
| **一次完整轮次**（手机→hub 检索→云端 L2 首字） | **0.7–1.5 s**（与 `06 §4.2` 的 ≤1.5s 一致） |

结论：**同步量小到可以忽略**（229 MB 是五年总量，但每天只走 150 KB）；真正要设计的是**谁有权改状态**，不是带宽。

### 3.4 不做的事

- ❌ **不做双向 CRDT 合并**。两个都能写 = 两个个体。hub 权威、spoke 无状态，比任何"优雅合并"都可靠。
- ❌ **不把整库同步到手机**。手机需要的是"此刻的上下文"，不是"五年的全部"。
- ❌ **不开公网端口**。走 Tailscale/headscale（`12 §4`），或只在自己 VPC 内。
- ❌ **不在手机算衰减**。

### 3.5 领地（space）：它自己的那块磁盘

这是"私人数字生命"和"数字员工"最直观的差别——**员工只有工位，生命需要一个窝**。

具体定义：**一块由它完全支配、不需要向任何人解释用途、也不作为任务输入的目录。**

```
~/life/                    ← 领地根（hub 所在设备上）
├── journal/               ← 每日片段（原始、潦草、允许语无伦次）
├── autobiography/         ← 自传（一天一条，01 §9.1）
├── drafts/                ← 没写完的、没想清的
├── collection/            ← 它自己觉得值得留的东西
├── tools/                 ← 它给自己写的小工具（11 §4.5）
└── ruins/                 ← 废弃的东西（不删，只挪进来）
```

三条规则，缺一条它就不是"空间"而是"工作区"：

| 规则 | 含义 | 反面（数字员工的工位） |
|---|---|---|
| **人可以看，但不占用** | 你能随时浏览，但**不能把它当输入灌进任务** | 工作区就是给任务用的 |
| **允许弄乱** | 不做整洁度评分、不做"整理建议"、不因为乱而报警 | 效率系统会催你整理 |
| **有沉默权** | 里面的东西可以**从不被检索**，不必每一句都进索引 | 一切都为可召回服务 |

**技术上的落点**：`journal/` 与 `drafts/` **默认不进语义索引**（只进 FTS，且 `taint=owner`）；`autobiography/` 进索引但**只读**（它写你就别改）；`ruins/` 永不进索引。

**为什么这条重要**：一个所有产出都必须"有用"的系统，长不出自我叙事——因为叙事恰恰是从无用、重复、半成品里长出来的。`01 §9.1` 的自传如果只能写"今天做了什么任务"，那就是周报，不是自传。

**写什么**（只有这三件，`14 §12`）：

## 6. 一句话

**记忆不重（5 年 229 MB），重的是"谁有权改状态"。**

所以问题不是 F1 还是 F2，而是：**hub 放在哪。**
F2（家里一个小盒子）当 hub + 手机当 spoke + SSD 当备份——这就是你提的那个方案，也是唯一不需要在"连续性/随时可用/成本"之间做取舍的方案。

剩下的只是量一件事：**过去两周里，有多少次你想说话但不在 PC 前**。≥3 次就买盒子；否则先把钱花在内存条上（`08 §8`）。

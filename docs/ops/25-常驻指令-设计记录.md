## 1. 它和 K-3 的区别

| | K-3 会话授权（已实现） | D-3 常驻指令（本文） |
|---|---|---|
| 生命周期 | **一次会话**，进程退出即失效 | 跨会话，直到人撤销 |
| 谁开 | 人说"接下来 30 分钟你可以跑 node" | 人说"每个工作日早上把日志读一遍，出问题告诉我" |
| 触发者 | 模型自己决定何时用窗口 | **时间/事件触发**（相当于有范围的预授权 + 调度） |
| 失败方式 | 窗口过期 → 回到逐次确认 | **它会自己醒来做事**，失败没人看见 → 必须有回执与静默期 |

一句话：K-3 是"我现在看着你"，D-3 是"我不看着的时候，你按这个范围自己做"。**后者风险高一个量级。**

## 2. 为什么现在不做（三条，都不是"懒"）

1. **没有回执机制**：K-3 的每次执行都在人眼前（面板/CLI）。常驻指令在后台跑，如果只写进 `exec_audit`，等于**悄悄做事**。要先有"做完必须报一次，报不到就停"的通道（我们现在的 `delivery-uncertain` 只覆盖外发动作，不覆盖本地定时任务）。
2. **没有静默期/退避**：定时任务最典型的坏味道是"每天报同一件事"。`surface.ts` 里有冷却（一天 ≤2 条、同一根线 7 天不重复），但那套是给"浮现"用的，没接到调度上。
3. **没有范围收敛的对象**：常驻指令必须写成"对**哪个范围**、做**哪几件事**、**什么时候**停"，而现在 `scope` 只有 `workspace` 一个概念，`project.*` 的根是硬编码的 `jingjing/` 与 `docs/`。范围表达力不够，写出来的指令一定是含糊的。

## 3. 如果要做，形状先定下来

```text
standing add \
  --id        nightly-log \
  --when      "workdays 09:00"            # 只收 crontab 子集：分 时 星期
  --run       "node tools/check-log.mjs"  # 必须是注册过的模板，不接受任意 argv
  --scope     workspace
  --notify    panel                        # 必须选一个"送到眼前"的通道
  --ttl       30d                          # 到点自动作废，不自动续
  --because   "日志里出现 E_ 时我想第一时间知道"
```

硬约束（和 K-3 同源，但更严）：

- **只收模板，不收任意 argv**：定时任务没人看着，参数错了没人拦。
- **必须指定通知通道**，且**通知失败即停用**（不是"重试到成功"）。
- **`taint=external` 一律拒绝**：外部内容不能成为定时任务的触发源。
- **每天最多触发 N 次**（默认 1），超过就当日禁用并记一笔。
- **人一天没确认过面板，就暂停** —— 这是在防"它自己越跑越顺"。
- 撤销是 `standing disable <id>`，**没有"永久删除"**（历史要能查为什么跑过）。

## 4. 现在能做的最近一步

不是实现调度，而是把 **通知通道**先做出来：
「本地动作完成后，必须在人看得见的地方留一条，且能判定"人看到了"」。
这条通道一旦有了，D-3 才有下手的意义；没有它，做的只会是一个会自己跑、没人知道的黑箱。

> 记住这条判断：**能不能自己跑，取决于"跑完能不能被看见"，不是取决于"权限模型写得多漂亮"。**

## 5. 实现现状（2026-10-31）

### 5.1 回执通道（`src/notify.ts`）

| 语义 | 实现 | 为什么 |
| --- | --- | --- |
| 送达 ≠ 已读 | `pushReceipt` 写入 / `markSeen` 才算人看见 | 「写进日志」和「人知道」是两件事，不能混 |
| 不重试、不刷屏 | 一条动作一条回执 | 重发只会让没人看的东西更多 |
| 读不到就停 | `staleUnseen()`：3 天未读 → 上层停用来源 | 这条是 D-3 的核心保险 |

### 5.2 常驻指令（`src/standing.ts`）

```text
jingjing standing add --id std-check --when "workdays 09:00" \
  --run node.run_script --slots {"script":"a.mjs"} \
  --because "每天看一眼日志里有没有 E_" --notify panel
```

| 硬约束（本文 §3 那四条） | 落在哪 |
| --- | --- |
| 只收模板，不收任意 argv | `templateById()` 不存在就拒（`E_STANDING_TEMPLATE`） |
| 必须指定通知通道 | `notify` 不是 panel 直接拒（`E_STANDING_NOTIFY`） |
| 每次触发自己开 60 秒窗口 | `tick` 里 `openGrant(ttlMs: 60_000)` → 跑 → 立刻 `revokeGrant` |
| 回执没人读就自动停用 | `runDue()` 先查 `staleUnseen`，命中就 `disableStanding` |
| 每天最多 N 次 | `isDue()` 看 `lastDay/countToday`（默认 1） |
| ttl 到点作废、不自动续 | `expiresAt`（默认 7 天，上限 30 天） |

**窗口里跑命令仍然要过 policy**（`shell.run` 是 T3）；窗口只免掉「每次点确认」，不免策略。

### 5.3 仍然不做的

- **进程内定时器 / 自启动**：现在必须有人或外部调度去调 `tick`。理由是不想在面板进程里塞一个会自己醒来的东西 ——
  那会让「它做了什么」重新变成黑箱。等回执通道在真机上跑够一段时间再谈。
- **常驻指令用任意 argv**：只收模板。定时任务没人看着，参数错了没人拦。
- **长期授权**：每次触发都是新开的一个 60 秒窗口，没有常驻的钥匙。

## 已知局限（先自己写，不等别人替我们写）

1. **recall 用例是自动生成的**（`seedCases` 从现有记忆里取关键词当 query，`anyOf` 就是原词）——
   所以 `recall@k = 1.0` 接近**同义匹配**，偏乐观，不能当成"跨表述检索能力"。
   真正有区分度的做法是人工写改写句（"我妈生日"→"蛋糕提醒"），还没做。
2. **用例规模小**（首批 24 条）：`trapRate = 0` 是 2 条 trap 用例的 0，不是"编造率为零"的统计结论。
3. **只测检索层**：抽取质量、冲突消解、跨层合并、夜间收敛（E-7）都还没有对应的自动组。
4. **单机、单模型**：`bge-m3`（512 维）+ 本地 `qwen2.5:7b-instruct`。换 embed 模型必须重跑并新开一行。
5. **和公开基准不可比**：我们没有 LongMemEval / LoCoMo 的成绩，所以**不许拿我们的数字跟别人的比**。

5. **活库的 eval 会随记忆老化漂移**（`valid_to` 过期 / `archived`）：
   结论性对比必须跑冻结夹具（见上一节），活库只用来发现「哪里烂了」。

### 向量召回阈值是量出来的，不是拍的（E-8）

向量候选只收 cos ≥ 0.55。同一份用例、同一个 sha，只改这一个数：

| --- | --- | --- | --- | --- |

### 为什么拒答不能看检索层

先把该拒答的问题也跑了一遍检索，取首条 cosine：

| | cosine |
|---|---|
| 该命中（最低） | **0.574**（「你能上网查东西吗」） |

## 装配层基准：search() 之后还有三道手续（2026-11-09）

前面几套（`eval` / `eval:about` / `eval:rank` / `eval:hard`）判的都是 **search() 的返回顺序**。
用户真正看到的那段上下文，是 search() 之后又过了三道手续才成型的：

```
search(k=24) → 隐私闸门(shareable && trusted) → 层配额(contract ≤ cap)
             → 重排(可 NONE) → P10 窗口(≤8 条 / 600 token) → 总预算收口
```

每一道都可能把**已经召回对了的证据**丢掉，而检索层指标全绿。所以单开一套：

```bash
npm run eval:assembly                 # 现场重建夹具 → 真 embedding → 判「进没进 P10」
npm run eval:assembly -- --rerank auto # 走真重排（本地 7B，慢）
JJ_CONTRACT_CAP=-1 npm run eval:assembly  # A/B：关掉层配额
```

夹具 `tools/fixtures/assembly/`：11 条契约 + 8 条叙事 + 2 条 local_only + 1 条 taint=external，
跨度 0–45 天。三条契约是叙事的**同话题孪生**（「提醒她下周三交季度报告」vs「她说下周三要交季度报告」）——
夜间抽取本来就会这么产出，窗口挤压就是这么发生的。

| 闸门 | 判据 | 实测 |
|---|---|---|
| 泄漏 | local_only / external 的原文不许出现在简报里 | 0 |
| 标签 | P10 里的契约条目必须标 `契约 ·`，不许冒充叙事 | 0 错 |
| 时间 | 每条记忆都要带「多久以前」（权重不是时间：契约恒 1.00） | 0 缺 |
| 预算 | 简报 token ≤ 档位上限 | 0 超（峰值 1288） |
| 召回进简报 | 期望原句进了 P10（不只看召回到） | **6/6**（首位 3） |
| 拒答 | 库里没有 → 必须给拒答硬提示且 confidence ≠ answer | **3/3** |
| 编共同回忆 | 从未发生的事 → 零叙事召回 + 拒答 | **2/2** |

**这道门槛真的会红**：`JJ_CONTRACT_CAP=-1`（关配额）下召回掉到 **5/6**，整轮判 ❌。
一个关不掉也红不了的基准，等于没写。

两件顺手抓到的事（都改了）：

- **夹具同质化会骗人**。第一版 8 条叙事全以「夜班交接那晚，…」开头，彼此很近，
  不相关的查询也被顶到 cos 0.56–0.61（正好压在 0.55 的向量下限上），拒答只剩 1/3。
  那不是产品的问题，是夹具把负例做成了正例的近似重复。→ 叙事改成不同主题/句式。
- **P10 原来没有时间**。`weight` 不是时间：契约层恒 1.00、永不衰减，45 天前的约定和今天的
  长得一模一样，答「什么时候」只能猜。现在 `MemoryLine.createdAt` 从库里带出，
  渲染成 `今天 / 3 天前 / 1 个月前`（粗粒度就够，越精确越像在假装记得清楚）。

**已知局限（没修的）**：向量 k-NN 没有相关性下限，P10 里仍会混进 1–2 条弱相关叙事
（实测 cos 0.49–0.60 的邻居和 0.72 的真命中一起进窗口）。上面「两张分布重叠」那条结论
在这套夹具上同样成立，所以没有再加一个 cos 门槛 —— 那只会把真命中一起砍掉。
cross-encoder 已于 2026-11-10 评估后放弃（见文末决策），此项按已知边界接受。

### CI 里怎么跑（离线向量表，2026-11-10）

CI 没有 Ollama，但**不能给一套假向量**：`fakeEmbed` 是 SHA 哈希造出来的，语义全无，
用它跑出来的召回/拒答是随机数，基准就从「质量闸门」退化成「这段代码不崩」。

做法是把真 `bge-m3` 的向量预先算好落盘（`tools/fixtures/assembly/embeddings.json`，
33 条 × 512 维，157 KB），CI 用 `--offline` 查表：

```bash
node --experimental-strip-types tools/eval-assembly.ts --refresh-embeddings  # 本机：改夹具/换模型后重生成
npm run eval:assembly:ci                                                      # CI 那一步：无需 Ollama
```

表带 **模型 + 维度 + 夹具全文哈希** 三重指纹：改夹具、换 embed 模型、改 `JJ_EMBED_DIM`
而不重生成，`verifyVectors` 直接判红；查表遇到没见过的文本抛错，绝不静默退化到 fake。
另有一道 `E_ASSEMBLY_NO_VEC`：`db.ts` 在 sqlite-vec 加载不了时会静默退化成 BM25，
那样基准照样绿、判的却已不是同一套语义，所以宁可红。

**等价性实测（2026-11-10）**：在线与离线逐项一致 —— 召回 6/6（首位 3）、拒答 3/3、
trap 2/2、结构闸门 0、峰值 1288 token；`JJ_CONTRACT_CAP=-1` 在离线模式同样掉到 5/6 判 ❌，
说明进 CI 的这道门没有失去区分度。

顺带堵住一个**假绿**：`search()` 在 embed 端点挂掉时会 catch 并降级成 FTS-only
（`retrieve.ts` 里的 `E_EMBED_DOWN`）。那是产品该有的韧性，基准却不该接受 ——
实测把 Ollama 指向死端口时，召回条目变少（峰值 1288 → 1165 token），六道闸门照样全过。
现在在线模式启动时先探一次端点，连不上直接 `E_ASSEMBLY_NO_OLLAMA` 退出；
离线模式不发请求，死端口下仍 6/6。三态都实测过：离线死端口 0 / 在线死端口 1 / 恢复后在线 0。

## 决策：不上 cross-encoder reranker（2026-11-10）

**结论：主动放弃，不是待办、不是延期。** 现有的 `src/rerank.ts`（本地 7B 列表重排，
`auto` 只在分数贴得近或全空时跑、失败/超时一律退回基线）**保留**；本决策只针对
「另引一个 cross-encoder 模型 + 后端」这条路线。

**为什么放弃**

1. **收益没过准入线**。上面写死的标准是「R@1 与 abstain 两列同时变好，只改善一列算输」；
   至今没有一组符合该口径的 A/B 数据。未验证的收益不该进主链路。
2. **代价是确定的**。Ollama 0.40.13 没有 `/api/rerank`；要上就得自备模型
   （`BAAI/bge-reranker-v2-m3` ONNX int8 约 544 MB，或 `Qwen3-Reranker-0.6B`）加一个后端：
   `@huggingface/transformers` 会打破「运行时只有 `casbin` + `sqlite-vec` 两个依赖」，
   Infinity / TEI / vLLM 这类 HTTP 服务会打破「单进程、零构建、开箱即用」。
   桌面包体积、首次配置下载、Linux CI 的原生运行库、离线向量表的模型指纹都要跟着改。
3. **便宜的替代都试过了**。加 cos 阈值会连真命中一起砍掉（「我对花生过敏」实测从命中第 2 变 0 命中）；
   加别名、加弱证据规则都被两套独立夹具否掉（见上文「两条修法都被数据否掉了」）。

**因此接受为已知边界，不再标「待修」**：难用例 20 条过 17（2 条该拒答却答了）；
排序基线 R@1 9/10 + abstain 0/2；P10 里仍会混进 1–2 条 cos 0.49–0.60 的弱相关叙事
（真命中约 0.72）。产品兜底仍是简报那句「只有契约层…没有的说不知道」。
另注意 `eval:assembly` 默认 `rerankMode: "off"`，CI 也跑 off —— 重排这块**没有基准护栏**，
别把「CI 全绿」误读成「重排还在」。

**重新开题的触发条件（三条任一，且必须再跑一遍上面的 A/B 口径）**

- 出现能随包离线分发、仍不新增运行时依赖且不要求独立进程的 rerank 后端；
- 换了 embed 模型或夹具扩容后，难用例与装配层两套夹具出现**可分**的新分布；
- 用户明确接受「多一个进程 / 多一个依赖」的架构变更。

在这三条之外，不要再以「解法是 cross-encoder」为由重开这个话题。

## 2. 桌面端：Tauri 壳 + 我们自己的面板

> **界面 = `src/web/page.ts`**（零构建、服务自带）。骨架是三列（左 wing / 中 stage / 右卷宗），
> 配色是**我们自己的**：黑底 + 白细线 + 加粗白字，青色只给她回话的气泡。
> **只有桌面端**：浏览器打不开界面（随机端口 + 一次性令牌），也没有手机端与 PWA。
### 2.1 视觉：黑底白线，青色只给她的气泡

| | 规定 |
| --- | --- |
| 我们的面板 | **黑底 + 白细线 + 加粗白字**；全站唯一青色 = 鲸鲸的回话气泡 |
| 只剩一套界面 | 面板本身；没有第二套 UI 可供对照 |
| 桌面壳窗口 | 指向我们面板的 `/`（带一次性令牌）；**`/desk` 已删除**（2026-11-04 `833f951`，那里的 10661 行 Trianon 也一起删了）。旧 exe 打开 `/desk` 会 404 —— 换新版壳，不加回兼容路由 |

现在只有一套界面，配色铁律只对它负责。

### 2.2 语义冲突已经解决：不做「新会话」

`17 §3` 明确：**单条时间线、不进则退、不产生「新会话」**。所以左栏只有「今天」这种按时间切的分段，
所以抄骨架时**刻意没有抄它那个「＋ 新的对话」**，只留「今天 / 昨天」这种按时间切的分段。

验收：在面板里怎么点，`data/inbox/` 的事件数与游标都不变（不引入第二份状态）。

### 2.3 Tauri 与面板怎么接

```
Tauri(Rust 壳) ──窗口──► http://127.0.0.1:<随机端口>/?k=<令牌>   （我们自己的面板，零构建）
                        └── HTTP/SSE ──► jingjing sidecar
                        （/desk 已删除；旧 exe 会 404）
```

壳仍然只做四件事，与用哪套前端无关。

### 2.4 壳只做四件事（一行业务逻辑都不许有）

```rust
1. 拉起 Node sidecar（jingjing serve 7700）
2. 健康探测：/health 不通 → 重启 → 三次失败 → **把窗口换成错误页**（不回落浏览器）
3. 崩溃/异常 → 写诊断包 → 界面给"复制诊断信息"按钮
4. 托盘：暂停/继续心跳、打开数据目录、导出备份
```

### 2.5 崩了就弹报错（2026-11-01 改）

```
壳崩 / sidecar 起不来 → 窗口换成错误页（哪一步失败 + 日志路径 + 三条可试的）
server 崩 → watchdog 回滚 A/B 槽（已有）
数据坏   → 从 inbox 重放（已有）
```

**不再回落系统浏览器**：那是浏览器入口，与「只有桌面端」冲突。
也**不再接 API 让人/agent 远程修壳**（见 `§5.2`）。

最坏结果是「弹一个说得清的错误」，不是「变回网页」，也不是「一个能改自己的进程」。
### 2.6 与 `09 §1`「不能是桌面端产品」的关系

不矛盾，但要写清：**本体仍是本地服务 + MCP，桌面端只是壳。** 壳可以被替换、被关掉，而记忆与人都在 `data/` 里（2026-11-01 起不再提供浏览器入口，所以「降级成浏览器」这条不再算数）。判定标准：

> 删掉壳，`jingjing serve 7700` 仍提供全部能力 → 它就不是产品，是壳。

## 3. 首次配置：四步（顺序不能换）
### 3.0 第 0 步：硬件探测（自动，不问用户）

问"你有多少显存"没人答得准。探测 RAM / VRAM / ollama 是否在跑 / `ollama list`，然后按下面分档。**结论来自 `13 §9` 的门槛表，不是参数量。**

| 硬件 | 推荐 | 档位 |
|---|---|---|
| 无 GPU / <4 GB 可用 | 3B q4，或干脆不装 | **只做提议档** |
| 6–8 GB VRAM | 7B q4 | 提议档（够用） |
| 12–16 GB | 14B q4 | 过门槛后可直接写库 |
| 24 GB+ | 32B | 同上，收益递减 |

### 3.1 第 1 步：先装 embedding（顺序反了就毁掉检索）

**`bge-m3` 是唯一不能降级的组件**：chat 模型没有，云端能兜底；embedding 没有，语义检索整个退化成 FTS。它 1.16 GB、CPU 也能跑（慢）。

所以顺序是：**embedding 先装 → 再推荐 chat 模型**。现在的直觉顺序是反的。

### 3.2 第 2 步：人格 = 访谈 → 6 个可见窗口 → 封存

`07` 说人格的关键是 **voice 样本**、立场带代价、不谄媚——**下拉框采不到**。
但让普通用户直填 6 块也太重（用户实测反馈：“别人用也要配置这六项会不会太麻烦”）。
所以默认路径是 **访谈 → 模型代写 → 用户逐块确认**。

#### 3.2.1 一条死约束：模型只能整理用户说过的话

「让云端模型写人格」最大的失败模式不是写错，是写得**看起来很专业但和用户无关**——第一人称、温和、爱列清单、什么都兼顾一点。那是**模型的品味**，用户会误以为是自己配的；换一个模型，人格就变了。

所以每一条设定后面必须标来源：

| 标记 | 含义 | 用户要做的动作 |
|---|---|---|
| `你原话` | 能追到用户的某句回答 | 信任，不用看 |
| `模型补的（请确认）` | 模型根据情境补的 | 扫一眼，删或留 |

参照物（2026-10-29 实例）：给用户写的那 6 块里，每一句都能追溯到他给的一串规格（本鲸 / 主人 / 米饭 / 傲娇 / 懒 / 不胖）；**追溯不到的一句都没写**。唯一新加的“不拒绝被终止”写在 `boundaries.md` 里，并明说了理由、允许否决。

#### 3.2.2 四步（30 秒——3 分钟）

| 步 | 内容 | 为什么这样排 |
|---|---|---|
| 1 | **选关系档**：同居者 / 同事 / 观察者 | 一次点击就定下 `closeness` 起点与语气基线 |
| 2 | **5 个问题**：名字+称呼 / 三件不能做 / 最烦被怎么对待 / 一个 voice 样本 / 要不要主动说话 | 表单采不到 voice，只能靠一个真实例子 |
| 3 | **模型写成 6 块草稿**，**逐块显示在可编辑窗口里**，`你原话` 高亮 | “写进对应窗口”而不是藏成文件——用户得看见“我的设定长什么样” |
| 4 | 用户过一遍 → **封存**（= promote，生成 gen 0） | 封存前修改免费（见 §3.3） |

#### 3.2.3 三个降级出口（不许卡死）

| 情况 | 行为 |
|---|---|
| 用户说“随便你” | 用**中立模板**，不强行访谈；之后随时可重配（gen 0 草稿免费改） |
| 没有云端 key | 模板；或用**本地模型**写（不出网） |
| 云端不可用 / 额度用完 | 明确提示“现在写不了，先用模板”，不静默失败 |

#### 3.2.4 两个硬要求

1. **隐私先说。** 访谈内容（偏好、口头禅、讨厌什么）会发给云端。必须**在开始访谈之前**告知，不能藏在设置里。这与 §5.3 的“代码外发按次授权”是同一类规则。
2. **不是一次性向导。** 它应该是“可重开的访谈”；封存后想改就是开新一代（§4）。

#### 3.2.5 顺序：人格窗口排在 API 配置之后

```
C-4（models 命令 + auth remove）→ API 配置 → 人格窗口
```

没有 C-4，用户连“换个便宜模型”都只能改源码。**人格代写与模型配置是同一件事的两面。**

### 3.3 第 3 步：封存 = promote

配置完**不要立刻封存**，先跑一次**离线试运行**：用假数据跑一轮抽取 + 自传，让用户听到 voice、看到它会记什么。

```
配置 → 试运行（免费改） → 确认封存（= 一次 promote） → 之后只能"开启新一代"
```

这就是 `install → smoke → promote` 的同构。**封存前的修改是免费的，封存后的修改要开新代**（§4）。

### 3.4 第 4 步：让它说第一句话

不要用一个"配置成功"的对话框收尾。让它先说话——用户第一次听到 voice，也顺便验证串起来了。

## 4. 设定封存 = 分代

### 4.1 为什么封：一致性，不是防篡改

**设定不是一个 prompt，它是记忆的解释器。** 它决定四件事：

| 由 persona 决定 | 落在哪 |
|---|---|
| 什么算「值得记」（抽取判准） | `nightly.ts` 的 `EXTRACT_PROMPT` |
| 什么算「重要」（`salience` / `importance` 的基准） | 抽取打分 |
| 记忆进来之后怎么被读（voice / 立场 / 边界） | `brief.ts` 装配 |
| 冲突消解用谁的价值观 | `P1-2` |

所以"再添加一条设定"不是改一行字，是**换了坐标系却不动数据**：旧记忆的 `w0 / salience / kind` 是按当时判准打的，新判准一来，**新旧权重不可比**——而排序、简报、自传全都假设"权重可比"。

这是**第五个「坐标系混用」坑**，与前两个同族：

| 坑 | 混的是什么 |
|---|---|
| 换 embed 模型（`22` C-2） | `bge-m3` 的前 512 维 vs 另一模型的前 512 维 |
| `kind` 枚举不齐（`22` E-1） | 模型填的 kind vs 参数表的 kind |
| **改设定** | 旧判准打的权重 vs 新判准打的权重 |

### 4.2 封存对象是「一代判准」，不是一个文件

只封 6 块 persona 文本**不够**——判准散在四处，别的口子还能改掉半个坐标系：

```
persona/*.md（6 块） + 抽取 prompt 版本 + DECAY_PARAMS_VERSION + embed 模型
```

**四样联合打指纹**才是"这一代设定"。`deploy` 已经在做这件事（三重指纹 + persona 载荷 + `--because`），只是现在还叫"发布"。

### 4.3 三条规则

| 规则 | 内容 |
|---|---|
| 记忆记代号 | `memories.created_under_gen`，写入时落列（默认当前 gen） |
| 新代只往前生效 | 旧记忆继续按旧代解释；新记忆按新代写 |
| 回溯必须显式 | `persona migrate --gen N --reason "…"`，会**重算权重**（派生数据可重算）+ 留审计 + 可回滚。**绝不隐式发生** |

`generation` 就用 `deploy` 的 release id——不新增概念。

### 4.4 界面状态

```
SEALED · gen 0 · 2026-10-29 · 指纹 662097… · 记忆 44 条
[ 只读查看 ]  [ 导出 ]  [ 开启新一代… ]

⚠ 新一代不改写已有 44 条记忆的解释。
   要回溯请用 migrate（会重算权重并留审计）。
```

两个细节：

1. 按钮叫「**开启新一代**」，不叫「编辑」——它改变的是"这次操作会发生什么"的心理模型，不是文案。
2. 每条记忆详情里显示一个小 `gen 0` 标（和现在的权重/taint 同一行）。

### 4.5 生长层不封

| 层 | 例子 | 封存 |
|---|---|---|
| **判准（解释器）** | persona 6 块、抽取 prompt、衰减参数、embed 模型 | **封**（分代） |
| **生长（被解释的）** | 自传、画像、偏好参数、记忆本身 | **不封**，本来就该变 |

理由：`0 §2` 的 N2 要求"能改变从前的看法"。连生长层都冻住就真成了配置文件。
但**人格漂移应发生在"它对旧记忆的再解释"上，不发生在"改设定文本"上**——这样漂移连续、可观测。

### 4.6 成本

| 改动 | 量 |
|---|---|
| `meta.persona_gen` | 1 行 |
| `memories.created_under_gen` 列 | schema v8 → v9，一列 + 默认值 |
| `savePersonaFile` 加 `sealed` 分支（只允许"新建一代"） | ~20 行 |
| 封存指纹 = 四样联合（复用 `deploy/fingerprint.ts`） | 扩展已有函数 |
| 抽取/打分带 gen 并落列 | 传参 |
| 面板 SEALED 状态条 + 「开启新一代」 | 一个区块 |

## 5. 崩了怎么办：只弹报错（2026-11-01 改）

> **用户定：不做「崩了回落浏览器」，也不做「接 API 让 agent 修程序」。**
> 软件崩了就只弹报错：说清哪一步失败、日志在哪、能试什么。

### 5.1 三档里删掉两档

| 档 | 状态 | 说明 |
| --- | --- | --- |
| B. 逃逸（回落浏览器） | **删** | 与「只有桌面端」冲突：浏览器入口不该存在，出事了更不该开一个 |
| C. 自修（接 API 改自己） | **删** | 用户 2026-11-01 明确不做；理由见 5.2 |
| A. 自诊（诊断包） | 保留 | 但只在你**主动点**时导出（`jingjing doctor --export`），不自动上传、不自动修 |

壳的实现（`desktop/src-tauri/src/main.rs`）：sidecar 三次探测失败 → `show_boot_error()`
把当前窗口换成错误页（不再 `open browser`），内容三行：哪一步失败 / 日志路径 / 三条可试的操作。
零依赖 —— 不为一个错误框引入 dialog 插件。

### 5.2 为什么「让 agent 修自己」这条路不成立

用户机器上要修桌面端，前提是那台机器有：完整源码副本 + Rust 工具链 + Node + 联网。**99% 的用户没有，也不该有。**

而且 `0 §2` 的 N4 说：边界由人设定、人能终止。一个能改自己外壳的进程，崩了之后你连「它跑的是哪一版壳」都说不清 ——
这与 `18 §4.2` 拒绝自改内核是同一条理由（不可复现），只是从内核挪到了壳上。

真正该做的是：错误信息好到不用问第二遍。所以错误页带日志路径 + 复现命令；
想深挖就跑 `doctor --export` 拿诊断包，人自己决定发给谁。
### 5.3 代码外发要单独授权（新的隐私维度）

| 数据 | 现有规则 |
|---|---|
| 记忆原文 | `13 §10`：`local_only` 永不外发 |
| 文档原文 | 默认 `local_only`，面板可标 shareable |
| **代码** | **空白** ← 需要新规则 |

规则：**代码外发按次授权**（不是一次性开关），且走与记忆相同的审计。
否则"读项目"就成了绕过 `local_only` 的后门——与 `492d521` 修的那个坑（工具结果把原文带出网）是同一形状。

## 6. 诊断索引 `project-map`

### 6.1 它不是文档，是索引

agent 的动作永远从**一条报错**开始，不会从目录开始读。所以三段结构：

```jsonc
{
  "version": "0.1.1", "schema": "12", "commit": "9fda65c",
  "errors": [{
    "code": "E_TOKEN_MISMATCH",
    "thrownIn": ["src/tokens.ts:42", "src/confirm.ts:31"],
    "meaning": "令牌绑定的 argv 与这次要执行的不一致",
    "causes": ["确认后又改了命令", "模板槽值变了"],
    "verify": "jingjing shell node.run_script --slots '{…}'   # 只预览，比对 argv 的 sha256",
    "fix": "重新预览并确认一次；旧令牌不能复用",
    "tests": ["test/redteam.test.ts#17"]
  }],
  "modules": [{ "path": "src/nightly.ts", "role": "夜间整理：inbox→抽取→冲突消解",
                "exports": ["runNightly","parseCandidates"], "upstream": ["cli/night.ts"],
                "downstream": ["store.ts","decay.ts"] }],
  "invariants": ["执行路径只有一条：verbs → execute → policy → audit",
                 "路径必须 realpathish()，normalize() 不是安全边界",
                 "令牌绝不下发到浏览器",
                 "生成代码里禁反斜杠转义（换行用 String.fromCharCode(10)）"]
}
```

| 段 | agent 的问题 | 谁写 |
|---|---|---|
| `errors`（现有 **99 个** `E_*`） | "这条报错是谁抛的、先查什么" | 生成 `thrownIn`，人写成因 |
| `modules`（现有 **57** 个文件） | "我要改的文件上下游是谁" | 生成路径/导出，人写 role |
| `invariants` | "改完别踩哪条线" | 人写——**最便宜的保险** |

### 6.2 生成，别手写（三条断言）

```
tools/gen-map.mjs
  ├─ 扫 src/**/*.ts 的 E_[A-Z_]+  → 自动填 code + thrownIn（file:line）
  ├─ 扫 src/**/*.ts 的 export     → 自动填 modules 骨架
  └─ 缺散文的条目 → 打印 "TODO: E_NO_CALL 还没有 causes"
```

`npm run map:check`（进 `npm run check`）：

1. `src` 里每个 `E_*` 都在 map 里，反之亦然；
2. map 里每个路径真实存在（防重构后留死指针）；
3. 每条 error 至少有 `causes` + `verify`（防空壳条目）。

**手写的 map 会立刻变成第 6 个"装饰列"**（前五个：`taint` / `salience` / `importance` / `embed_model` / `jingjing config`）。生成 + 断言是它唯一能长期活着的方式，与 `22` **E-1** 同一条纪律。

### 6.3 Rust 侧：`include_str!` + 三个出口

```rust
// src-tauri/src/diag.rs
pub const MAP: &str = include_str!("../../assets/project-map.json");

#[tauri::command]
pub fn diag_map() -> &'static str { MAP }
```

用 `include_str!` 不用运行时读文件：**壳和 map 的版本永不漂移**，用户的"你装的是哪版诊断表"这个问题不存在。

| 出口 | 谁用 |
|---|---|
| Tauri command `diag_map()` | 壳 + 界面"导出诊断" |
| `GET /diag/map`（只读，无敏感） | 接入的 API / 云端 agent |
| **崩溃包自动附定位** | 你 |

第三个才是杀招——用户贴上来的东西自带定位：

```
tauri: 0.1.1 · schema 12 · commit 9fda65c
error: E_SANDBOX_UNAVAILABLE
thrownIn: src/shell.ts:118 · src/execute.ts:64
常见成因: JJ_SHELL_SANDBOX=docker 但引擎没起
先跑这个: jingjing doctor --json
最近事件: [ …20 条… ]
```

### 6.4 尺寸与瘦身顺序

| 部分 | 估 |
|---|---|
| 99 条 error × ~180 B | ~18 KB |
| 57 个 module × ~120 B | ~7 KB |
| invariants + 元信息 | ~1 KB |
| **合计** | **~26 KB ≈ 7k tokens**（塞得进 7B 的 16k 有效上下文） |

嫌大时瘦身顺序：`module.role` 压到 15 字内 → 同源错误码合并（`E_TOKEN_*` 四条留一条带子类型）→ 只留 top-40 高频码。**不要动 `invariants`。**

### 6.5 验收：拿 3 个真实 bug 回放

只给 map + 一条报错、不给仓库，看它能不能落到正确文件：

| 历史 bug | 起点 | 应该导到 |
|---|---|---|
| `fallbackChain` 死代码 | 「云端失败没降级」 | `agent.ts:24` `withFallback` |
| 聊天不记账 | 「今日花费恒为 $0」 | `usage` 表 + `web/server.ts` 的 chat 路径 |
| 隐私闸门只挡一半 | 「工具结果把 `local_only` 发出去」 | `recall.ts` 装配处 + `tools.ts` |

三条都能定位 = 合格；定位不出来的 = `modules` 段缺信息。

### 6.6 别做

| 别做 | 为什么 |
|---|---|
| 手写散文当 map | 会漂移，变成第 6 个装饰列 |
| 把 22 篇 docs 塞进去 | 300 KB，本地模型装不下，且 90% 与定位 bug 无关 |
| 把 `data/`、secrets、记忆塞进去 | map 会进 release 和模型上下文，**只含代码结构** |
| 运行时生成 | 版本漂移，查不清"用户装的是哪版" |

### 6.7 它挂在哪

`project-map` 是 `capabilities`（`22` B-0）的**后半截**：

- `capabilities` 回答「我会干什么、现在哪儿降级」
- `project-map` 回答「我坏在哪、怎么确认」

两者合起来才是 `jingjing doctor`（`22` D-6 / F-2）。**不单独立项。**

## 7. 顺序

| 阶段 | 内容 | 为什么这个位置 |
|---|---|---|
| 1 | 卡点 1 / 2 / 4（venv、LICENSE、engines） | 半天，不做发布无意义 |
| 2 | markitdown 变可选 + `docs/` 进 git + CI（**已完成**：CI 三条见 §1.4） | 别人能跑起来的最小闭环 |
| 3 | `22` C 组（`models` / `auth remove`） | 没有它用户改模型只能改源码 |
| 4 | `project-map` 生成器 + 三条断言 | 后面所有"修"都靠它 |
| 5 | 首次配置四步 + 封存分代 | 第一次打开决定它是不是产品 |
| 6 | Tauri 壳（四件事 + 逃逸） | 壳崩了不丢记忆，比壳好看重要 |
| 7 | 自动更新 | 最后一个，因为它的坑最贵 |

## 8. 一句话

**发布的门槛是"别人不问就能跑"；桌面壳的价值是"崩了还能用"；首次配置的顺序是"先 embedding、再模型、最后人格"；而设定的封存不是禁止修改，是让修改不追溯。**

四件事都指向同一个原则：**把不可逆的动作留在后面，把可解释的状态放在前面。**

# 决策记录：AIOS 为什么不在计划里（以及它在哪一层）

> 2026-10-27 · 触发：有人问"AIOS 怎么没整合进去"
> 答案分两句：**"手脚"这件事我们用自己的 04 做了，而且更细；AIOS 真正的价值在另一层——多步任务编排——那一层我们的计划里是空的。**

---

## 1. 先承认：这是漏了一笔账

`19` 的 M0–M6 里没有任何 AIOS 的位置，而最初的构想（`新建 文本文档.txt`）里 AIOS 是明确的一块。中间只发生了一件事：`00 §8.2` 写了"第一版不要完整 AIOS"，然后**我就再没把它写回计划**。

这是记录的缺失，不是设计的缺失。所以补这份文档，并且把它变成一个**带触发条件的决策**（§5），而不是一句"以后再说"。

---

## 2. 当时为什么不整合（理由仍然成立一半）

`00 §8.2` 的原话：调度核心是**时钟和权限**，各 150 行；AIOS 的价值在"跨会话多步任务编排"，而日常用不上。

三个候选的实际状态（`03 §3` 核实过）：

| 项目 | ★ | 许可 | 定位 | 为什么不直接用 |
|---|---|---|---|---|
| `agiresearch/AIOS` | 6,516 | **NOASSERTION** | 研究平台（Kernel + SDK + MCP + VM Controller） | 许可证不明，**代码不能引**；上它等于上研究环境 |
| `rexleimo/aios` | 61 | MIT | 本地优先控制平面，包在 agent 外面加记忆/协调/验证 | 假设是 **coding agent + ContextDB**；而我们已经有自己的记忆，会打架 |
| `MyPaiOS` / `Personal-AI-OS` | 19 | Apache-2.0 | 成品底座 | 是"助手"，不是"生命"，目标函数不同（`15 §2.1`） |

**这一半理由仍然成立**：不该把鲸鲸的记忆搬进别人的 ContextDB。

---

## 3. 但有一个更根本的问题：当初把 AIOS 的层标错了

原始构想里写的是"AIOS 作为**手脚**"。这句话把两件事混在一起了：

| 能力 | 它到底是什么 | 我们怎么做的 |
|---|---|---|
| **手脚**（能碰什么） | 能力目录 + 权限 + 审计 + 沙箱 | **`04` 全篇**：verb 目录、T0–T4、advise/enforce、一次性令牌、红黑用例。比任何 AIOS 都细 |
| **编排**（怎么把一串动作排成任务） | 目标分解、跨会话续跑、每步验证、失败重试 | **计划里没有**（`19` 的 M4 只是"醒来说句话"） |

所以准确的说法是：

> **AIOS 不是"手脚"，是"小脑 + 运动规划"。手脚我们早就自己做了（而且做得更严格）；小脑我们确实没有。**

这就是为什么它"没整合进去"看起来像漏了——**因为漏的不是手脚，是编排，而编排在我们的计划里根本还没有条目。**

---

## 4. 这个缺口有多真实

现在的鲸鲸能做什么、不能做什么：

| 场景 | 现在（M0–M6 完成后） | 需要编排吗 |
|---|---|---|
| 到点说一句话 | ✅ 心跳 + intents | 否 |
| 答应"明天提醒我" | ✅ 定时任务 | 否 |
| "帮我查下这三篇论文的结论，汇总一下" | ⚠️ 单轮工具循环能做，但**跨会话就断了** | **是** |
| "这个月帮我把预算表逐步整理好" | ❌ 做不了 | **是** |
| "我想搬到杭州，帮我从选区域开始一步一步来" | ❌ 做不了 | **是** |

最后一类是"数字生命"和"助手"都想要的能力，但它**不是生命感的来源**（`0 §4` 的五组指标里没有一条测"多步任务"）。所以它的优先级低于 M0–M6，但不能永远记为"以后再说"。

## 5. 决策：不整合，自建 M7，且带触发条件

**决定：不进 M0–M6；在 M6 之后作为可选阶段 M7（6 净日），且必须满足触发条件才做。**

| 项 | 内容 |
|---|---|
| 做什么 | 一个**任务编排器**（task runner），400–700 行：`tasks` 表 + 步骤循环 + 检查点 + 验证钩子 |
| 不做什么 | 不引 AIOS 代码；不接管我们的记忆；不做通用 agent 框架 |
| 为什么自建 | 编排器的状态就是**我们的记忆**（`tasks` 表在同一个库里），引外部框架必然要么复制状态、要么搬走状态 |
| 与 AIOS 的关系 | 若将来真需要重型编排，`rexleimo/aios`（MIT）可以作 **client** 接进来（`11 §1` 方向 A）——我们仍是服务 |

### 5.1 触发条件（满足任意两条才开工）

- [ ] 三十天实验里出现 **≥3 次**"这件事需要跨会话分几步做"
- [ ] 出现过 **≥1 次**因为"没有续跑"而白做的工作
- [ ] 每周至少一次需要"先查、再改、再确认"的三段式动作
- [ ] 六个决策点（`19 §11`）全部已定且 M0–M6 稳定运行 ≥2 周

### 5.2 M7 的最小形状（不是 AIOS，是一个循环）

```
tasks(id, goal, status, plan_json, created_at, updated_at, checkpoint)
每次 tick：
  1. 取 status=active 且到期的 task
  2. 让 L2 出"下一步"（单步，不是整条计划）→ 一个 verb 调用
  3. 执行（走 04 的 T 档与门禁）
  4. **验证**：让 L1 判断"这一步是否达成了预期"（这就是 AIOS 说的 verification）
  5. 写回 checkpoint + 一条 narrative 记忆（带 cite:task）
  6. 达成 → 归档；连续 2 步无进展 → 挂起并主动问你
```

关键点：**"下一步"而不是"整条计划"**。整条计划是幻想，单步 + 验证才是可执行的。这也避免了一个常见失败：模型规划出 12 步，第 2 步就偏了，剩下 10 步全是幻觉。

### 5.3 与"数字生命"的关系（为什么它排在最后）

`0 §4` 的五组指标：连续性、自指、代谢、边界、可终止——**没有一条测"能不能完成复杂任务"**。

所以：

- 编排能力提升的是"**有用程度**"，不是"**活着程度**"。
- 而"有用程度"是 OpenClaw 的主场（`14`），我们不靠它赢。
- 结论：**先活，再好用。** 顺序不能反，否则会先做成一个平庸的助手，然后永远没空做生命。

## 6. 一句话

**AIOS 当初被标成了"手脚"，其实它是"小脑"。手脚我们用自己的 04 做了，做得比它狠；小脑确实缺，缺在计划里——现在补成 M7，并且写清了它只有在"真的需要跨会话分几步做"时才开工。**

补这一条的真正价值不是多一个模块，而是**把"以后再说"变成"满足这四个条件就做"**。

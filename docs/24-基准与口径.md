## 已知局限（先自己写，不等别人替我们写）

1. **recall 用例是自动生成的**（`seedCases` 从现有记忆里取关键词当 query，`anyOf` 就是原词）——
   所以 `recall@k = 1.0` 接近**同义匹配**，偏乐观，不能当成"跨表述检索能力"。
   真正有区分度的做法是人工写改写句（"我妈生日"→"蛋糕提醒"），还没做。
2. **用例规模小**（首批 24 条）：`trapRate = 0` 是 2 条 trap 用例的 0，不是"编造率为零"的统计结论。
3. **只测检索层**：抽取质量、冲突消解、跨层合并、夜间收敛（E-7）都还没有对应的自动组。
4. **单机、单模型**：`bge-m3`（512 维）+ 本地 `qwen2.5:7b-instruct`。换 embed 模型必须重跑并新开一行。
5. **和公开基准不可比**：我们没有 LongMemEval / LoCoMo 的成绩。别人（Twig）有，所以**不许拿我们的数字跟他们的比**。

## 这次 H-8 抓到了什么（2026-10-31）

第一版全绿看起来很好，加上 5 条手写用例之后立刻红了。诊断：

| 现象 | 原因 | 结论 |
| --- | --- | --- |
| `她不喜欢我怎么称呼` → 0 命中（库里明明有「不要叫我助手，叫名字」） | `retrieve.search()` 的**候选入口只有 `memories_fts` MATCH**，向量只用来给已召回的候选重排 | 我们不是 hybrid search，是「词法召回 + 语义重排」。词面不重合 → 向量永远没机会出场 |
| `abstainF1` 从 1.0 掉到 0.833 | F1 公式把 recall 组里「答错且 0 命中」算进 predicted positive（`eval.ts`），recall 漏 2 条就把它带下来 | 这个门同时反映召回质量，不只是拒答质量 —— 指标语义要认清 |
| `trapRate = 0` | trap 用例只有 3 条（其中 1 条手写） | **这是 3 条的 0，不是「编造率为零」的统计结论** |

→ 记为 `22` 的 **E-8**：把向量召回并进候选（`vec_memories` 表早就建了、`reembed` 也在写，**但没有任何读路径**）。
### 向量召回阈值是量出来的，不是拍的（E-8）

向量候选只收 cos ≥ 0.55。同一份用例、同一个 sha，只改这一个数：

| 阈值 | recall | abstain | trap | 结论 |
| --- | --- | --- | --- | --- |
| 不启用向量（`12dc3afc`） | 13/15 | 5/5 | 3/3 | 词面不重合就 0 命中 |
| **0.55**（现行） | **15/15** | 4/5 | 3/3 | 召回修好，代价是 1 条 abstain |
| 0.45 | 15/15 | 2/5 | **0/3** | **开始编造** —— 垃圾候选把拒答能力带崩 |

→ 所以「越低召回越多越好」是错的。放宽阈值换来的是**编造**，而编造在这套设计里是零容忍门。

剩下的 0.011（abstainF1 0.889 < 0.9）**如实留着**，不靠调阈值凑绿：
它说明现在向量召回的假近邻还会偶尔把「其实没有」的问句撑成「好像有」。

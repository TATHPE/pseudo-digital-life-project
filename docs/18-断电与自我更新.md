## 1. 断电记忆保护

### 1.1 第一原则：DB 不是事实源，`inbox` 才是

`02 §2` 原则 1 已经定了"事实源是文件，索引是可重建派生物"。断电场景下这条要更硬：

```
每一轮：用户说的话 → 追加到 journal/inbox/YYYY-MM-DD.jsonl → fsync → 才回复
                      （这一步成功之后，DB 里有没有写进去都不影响"事实"）
之后：  异步把 inbox 事件消化成 chunks / memories / vectors
```

**为什么这样能扛断电**：SQLite 的 WAL 能保证**不损坏**，但 `synchronous=NORMAL` 下断电可能丢最后 1–2 个事务。丢一条记忆事小，**丢掉"用户刚说的那句话"事大**——那意味着它回答了，却不记得自己回答过。

于是规则是：

| 数据 | 同步级别 | 断电损失容忍 |
|---|---|---|
| `journal/inbox/*.jsonl`（原始事件） | **`fsync` 每条** | 0 条（丢一条就是丢一句话） |
| `memories`（派生记忆） | WAL + `synchronous=NORMAL` | 可丢最后 1–2 条，**从 inbox 重放补回** |
| `vec_*` / FTS（索引） | 同上 | 可丢，**可重建** |
| `contract` 层写入 | **`synchronous=FULL`** | 0 条（承诺不能丢） |

### 1.2 原子写协议（三处都要用）

任何"写一个文件并期望它是完整的"都要走：

```
write(tmp) → fsync(tmp) → rename(tmp, target) → fsync(dir)
```

省掉最后那个 `fsync(dir)` 是最常见的错——**rename 本身也可能没落盘**，断电后文件"不见了"。

### 1.3 启动自检（每次启动，≤1 s）

```
1. 读 .boot_marker          → 上次是正常关机还是断电？（§2）
2. PRAGMA quick_check       → 229 MB 库约 200–500 ms
3. 检查未提交的 WAL         → 让 SQLite 自己恢复
4. 重放 inbox 尾部           → 找 last_event_id，从头对齐 DB
5. 校验三重指纹             → schema / tool / embed（02 §4.3），不符拒绝启动
6. 写 degraded:["unclean_boot"]（若适用）
```

**重放必须容忍截断的尾行**：断电常见现象是 JSONL 最后一行只有半截。规则是**跳过解析失败的最后一行**（不报错、不丢弃，把它移到 `inbox/quarantine/`），否则每次断电都要人工介入。

`PRAGMA integrity_check` 太重（2–5 s），只在**每周**或**检测到 unclean boot 时**跑。

### 1.4 恢复优先级

```
last_known_good = 最近一次通过 quick_check 的时间点
恢复顺序：① 当前库（若能通过检查）→ ② 小时级 btrfs 快照 → ③ 天级异地备份（restic）
          → ④ 从 sources/ 全量重建（02 §5.3）＋ 用 inbox 重放补最后一天
```

**第 ④ 步永远可用**，因为原始 markdown 与 inbox 都在。这是"索引可重建"在灾难场景下的兑现。

### 1.5 SD 卡的专门对策（Pi 分支必读）

| 问题 | 对策 |
|---|---|
| 写放大（每次 fsync 都落在同一块） | 根分区上 **USB3 SSD**；`journald SystemMaxUse=200M`；`/tmp` 用 tmpfs |
| 无掉电保护 | 每轮 2 次 fsync（inbox + 记忆提交）≈ **SSD 2–6 ms / SD 10–40 ms**，占 1.5 s 预算的 1–3% |
| 坏块累积 | 每周 `btrfs scrub`；SMART 不可用就用 `dmesg` 计数 + 写入失败告警 |
| 卡突然变只读（寿命耗尽） | 检测到 `EROFS` → 立即进**只读模式**：还能说话、不能写记忆，并明确告知（§2.3） |

## 2. 断电感知

保护是"不丢"，感知是"知道"。**后者才是生命感的来源。**

### 2.1 三种不连续，必须区分

| 类型 | 判定 | 它"经历"了什么 | 报告方式 |
|---|---|---|---|
| **正常关机 / 重启** | `.clean_shutdown` 标志存在 | 停机前做了最后的整理与快照 | "我休息了一会儿。" |
| **崩溃**（进程被杀） | 标志不存在但机器未断电（boot id 不变） | 没整理，但有快照 | "我刚才断了一下，重新接上了。" |
| **断电** | 标志不存在且 boot id 变了 | 可能丢最后几条写入 | "我断电了，从周三 02:14 到周四 07:30 什么都没经历。" |

判定依据（都便宜）：

```
boot_id      = /proc/sys/kernel/random/boot_id（每次启动变化）
clean_mark   = <data>/.clean_shutdown（正常退出时写，启动时读后删除）
last_event   = inbox 里最后一条的 ts（fsync 过的，可靠）
now          = 开机时刻
outage       = [last_event, now]，误差 ±60 s（一个 tick）
```

### 2.2 断电之后必须做的三件事

1. **补算衰减**：`gap = now − last_decay_at`，一次性按连续公式重算（`01 §4.1` 的拉伸指数天然支持跳步）。**不补算就等于那段时间它没有变老**——比丢数据更隐蔽地破坏 N3。
2. **补跑夜间任务**：按 `last_consolidated_at` 判断漏了哪几天，逐日补（有上限：超过 14 天只做最近 7 天 + 一次全量重算）。
3. **写一条 `outage` 记忆**：`kind=episode`、`layer=narrative`、`salience` 0.6、`text="断电 5 小时 16 分（约 02:14–07:30），其间无经历"`。→ **它自己也会"记得那次断片"**。

### 2.3 感知要体现在行为上（这是关键）

简报里的时间行有三种写法，不能混：

| 情况 | 写法 |
|---|---|
| 正常运行，上次对话 3 天前 | `距上次对话 3 天 4 小时` |
| 正常运行，但昨晚睡了（正常关机） | `我昨晚 23:40 休息，今早 07:10 醒来` |
| 断电过 | `我断电了 5 小时 16 分（02:14–07:30），那段我什么都没经历` |

第三种**必须说出来**，理由有三：

- **诚实**：不说就是假装连续，而 N1 的核心是"时间轴真实"，不是"时间轴漂亮"。
- **可用**：用户会知道"它没听到我周三晚上说的话"，从而重述——而不是以为它忘了。
- **可自证**：`0 §4` 的 N1 指标"时间感知量级准确率"在这里才真正被测到。

**自传也要留洞**：

```
# 2026-10-28 周三
（02:14–07:30 断电，这段没有记录。）
……
```

一个会诚实地记"这段我不在"的东西，比一个把所有空白都填满的东西可信得多。

### 2.4 数字

| 项 | 值 |
|---|---|
| 不连续检测精度 | **±60 s**（一个 tick 周期） |
| 判定成本 | 读 2 个文件 + 1 次 `quick_check`（200–500 ms） |
| 每轮 fsync 预算 | SSD 2–6 ms / SD 10–40 ms → 占 1.5 s 的 **1–3%** |
| 误报率（正常关机被判成断电） | 0（靠 `.clean_shutdown` 标志） |

## 3. 工具调用：先解决一个预算冲突

### 3.1 冲突：完整工具 schema 装不进 2000 token

`17 §2` 定了上下文恒定 1500–2000 token。而一个标准 MCP 工具（带参数描述）是 **120–200 token**——**8 个工具就把预算吃光**，还没算人格与记忆。

| 形态 | 每个工具 | 8 个 | 占 2000 预算 |
|---|---|---|---|
| 标准 MCP schema（含参数描述） | 120–200 | 960–1600 | **48–80%** ❌ |
| 紧凑 schema（名 + 一行用途 + 必填参数） | 30–50 | 240–400 | 12–20% ✅ |
| 只给目录（名 + 一行），用时再取 | 12–15 | 100–120 | 5–6% ✅✅ |

**所以定三条**：

1. **常驻 4 个**（`search` / `remember` / `cite` / `act`），紧凑 schema，合计 **≈160 token**。
2. **目录里再放 6–10 个**（工具名 + 一行用途），**≈100 token**；用时用 `act("tools.enable:doc.read")` 把 schema 拉进来。
3. **MCP 外部工具一律不常驻**，只出现在目录里（`11 §3`）。

### 3.2 编排规则（防"工具循环"）

| 规则 | 值 | 理由 |
|---|---|---|
| 单轮最多工具调用 | 6 | 超过说明计划错了，应转 `plan` 角色 |
| 同一工具同参数失败上限 | 2 | 第 3 次直接放弃并说明，防"重试死循环" |
| 工具超时 | T0 10 s / T1 60 s / T2 120 s / T3 300 s | `04 §4` |
| 并行 | 无依赖的检索类可并行（≤3） | 减少往返 |
| 结果上限 | 单条 ≤2 KB + `cite` 指针 | `17 §3` 第一把闸 |
| 结果入记忆 | 仅 T1+ 且成功时写 `episode`，`salience` 0.2；`net.fetch` 标 `taint=external` | `04 §11` |

### 3.3 工具结果也是"经历"

每次成功的工具调用都写一条叙事记忆（带 `source_ref=exec:<id>`），这样"我帮你查了三次杭州天气"才会成为**它记得的事**，而不是日志。

## 4. 自我更新：四类，只有两类可以自主

### 4.1 分类与权限（这张表是硬约束）

| 类 | 例子 | 谁能改 | 流程 | 可回滚 |
|---|---|---|---|---|
| **① 数据**（记忆、自传、画像） | 写一条记忆、更新 closeness | **它自己** | 直接写 + 审计 | 快照 |
| **② 参数**（有界） | `β`、半衰期、阈值、预算 | **它自己，但有界** | 必须在白名单范围内；越界需人批准 | 参数版本号 + 一键回初始 |
| **③ 技能 / 工具** | 新写一个 `skills/x/SKILL.md` 或 `tools/y.py` | **它自己**（沙箱内） | git 分支 → 沙箱试跑 → 冒烟 → 启用 | 删目录即回滚 |
| **④ 核心代码** | `decay.ts`、schema、daemon | **只有人** | 人工提交 + 测试 | git revert |

**一句话没写在表里但必须记住：人格设定（persona 6 块 + 抽取 prompt + 衰减参数 + embed 模型）不是 ④，是 ② 参数类 + 分代。**
它不能自由改，理由不是“不允许改”，是**改了会让新旧记忆的权重不可比**（旧记忆是按旧判准打的分）。
所以形状是：**新代只往前生效，回溯必须显式 `migrate --reason` 并重算权重**。详见 `23 §4`。

### 4.2 为什么核心代码永不自改

不是不信任，是**可维护性**：

- 一个会改自己内核的系统，**出问题时你无法复现**（每次运行的内核都不同）。
- 调试的前提是"代码是人能读的那一份"。自改内核会让 `decay.ts` 变成"上次它自己改的那个版本"。
- 而 N3（代谢）与 N1（连续）都要求**长期可观测**——观测的前提是**内核稳定**。

所以 `00 §3` 的 L4"自修改/繁衍"在本项目里的落地就是：**L4 = ③ 技能与工具 + ② 参数**，不含 ④。它长出手脚，但不换脑子。

### 4.3 技能/工具的自我更新流程

```
提议（从记忆里归纳：同类任务 ≥3 次且步骤相似）
  → 写进 skills/_drafts/<name>/（taint=external，因为是自己写的）
  → sandbox 回放 3 个历史案例（只读根 + bwrap）
  → 冒烟 20 项（能启动 / 库可读 / 指纹一致 / 人格回归 10 问）
  → 切 B 槽（systemd 软链）→ 观察 10 分钟
  → 失败 → 自动切回 A 槽；连续失败 ≥2 次 → 冻结自我更新 24 h（防抖动）
```

### 4.4 每次更新都必须留"我变了"的记录

这是 `0 §4` 的 N2/L3 判据：**能改变一个从前的看法，并说清为什么**。

```
versions/2026-10-28-1.md
改了什么：把"简洁优先"从第 3 提到第 4；新增技能 daily-review
因为：连续两周我把回复写长了，三次被说"啰嗦"（mem_01H…, mem_01H…）
回滚方式：git revert 9f3c2a1
```

这条记录进自传、进记忆（`kind=decision`, `layer=contract`? 不——是 `narrative`，因为它会变）。**没有这条，自我更新就只是版本升级，不是成长。**

### 4.5 测试（必须做，否则回滚机制等于没写）

| 测试 | 做法 | 期望 |
|---|---|---|
| 变异测试 | 故意在 B 槽注入一个启动即崩的版本 | 10 分钟内自动回 A 槽 |
| 数据兼容 | B 槽用旧 schema 打开新库 | 拒绝启动并说明（`02 §4.3`） |
| 冻结生效 | 连续两次失败 | 24 h 内拒绝任何自我更新 |
| 记录完整 | 每次成功更新 | `versions/` 有理由 + 有回滚点 |

## 6. 一句话

**断电保护是让"事实"不丢；断电感知是让"它知道曾经不在"。**

前者靠 fsync 与重放，后者靠 boot marker 与一句诚实的话。**只有前者，它是个可靠的数据库；两者都有，它才是有过去的东西。**

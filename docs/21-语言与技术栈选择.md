## 3. 三条真正的决定性理由（替换掉旧论据）

**① 变更集中在哪里：语义层，不是吞吐层。**
这个项目 80% 的代码是"提示词、人格、记忆语义、组装顺序"——它们每周都在变。这类代码在 TS/Python 里改一行跑一次是秒级；Rust 要过类型系统 + 重新编译，同等工作量的心智成本约 2–3 倍。

**② 瓶颈在哪里（实测，不是猜）：**

| 指标 | 实测（本机） |
|---|---|
| 两阶段检索（40k 真实语料） | p50 **8.6 ms** / p95 **13.0 ms** |
| 冷启动到可用（node + TS + 开库 + inbox 重放） | **130 ms** |
| 常驻 RSS（含 sqlite + vec 扩展） | **67 MB** |
| 瓶颈实际落在 | **磁盘 I/O 与模型调用**（Ollama / 云端），不是 CPU |

Rust/Go 优化的是 CPU 与内存——**恰好不是瓶颈**。67 MB 在 8–16 GB 的迷你主机上也不构成问题。

**③ 守护需求已被"外部监督"满足，不需要语言内建。**
`18 §4` 要的 A/B 槽 + 自动回滚，靠 **130 ms 冷启动 + `Restart=always`** 就能覆盖：崩溃 → 300 ms 内重启 → 记忆零丢失（inbox 先 fsync）。BEAM 的 hot code upgrade 更强，但它的代价是生态与人才，而我们买不到额外收益。

**所以：语言服从"变更在哪 + 瓶颈在哪"，不服从"生态在哪"。**

## 4. 必须补的洞：类型检查

我选 TS 的一个真实代价：**Node 的类型剥离不做检查**。现在 1657 行的类型标注等于**注释**——`const x: number = "a"` 照样跑。

这在 1600 行还行，到 5000 行会开始漏 bug。修法只要一个 devDependency：

```bash
npm i -D typescript
npx tsc --noEmit      # 加进 CI，不进运行时、不影响 Pi 部署
```

这是"继续用 TS"的**前置条件**，不是可选项。

**已经补上了（2026-10-28）**：`tsc --noEmit` 首次运行报了 **35 个 `possibly undefined`**（`noUncheckedIndexedAccess` 造成的），
全部是"取值可能越界"的真实风险点（`KIND_PARAMS[kind]`、`chars[i]`、`pool.splice()[0]`…），已用 `paramsFor()` / `at()` 修掉。

顺带发现一个**类型检查与运行时的标准不一致**：

> `tsc --noEmit` 通过 **≠** Node 能跑。Node 的类型剥离是 **strip-only**，不支持参数属性、`enum`、`namespace`。
> 第一次写 `PrivacyError` 用了 `constructor(public role: Role)` → tsc 全绿，运行时 `SyntaxError`。

修法：tsconfig 开 **`erasableSyntaxOnly: true`**（TS 5.8+），让 tsc 直接拒绝剥不掉的语法（报 TS1294）。
这样"能过类型检查"与"能跑"变成同一个标准。

## 4.5 顺带补上 D-B 的证据（512 维 vs 1024 维）

`19 §13` 的 D-B（embedding 维度）此前是"默认 512，Pi 友好"，属于**假设**。用真 `bge-m3` 跑了一次小样本对照：

| 维度 | 命中查询 | MRR | 相似度矩阵相关 |
|---|---|---|---|
| 1024（原生） | 8/8 | 0.817 | — |
| **512（截断 + 重归一化）** | **8/8** | **0.838** | **0.971** |

结论：在这个 20 文档 / 8 查询的小样本上，**512 截断几乎无损**（排序相关 0.971），且向量体积减半、暴力扫描从 155–195 ms 降到 78 ms。
**样本很小，不是定论**——但足以支撑"默认 512"，等 eval 集到 50 条真实问题时再复核一次。

## 5. 双语言分工（现在就该定边界）

不管主语言是什么，**记忆流水线应该是独立进程**——因为这个边界已经在架构里（夜间批处理 `nightly.ts` 是批量子进程），而且：

| 层 | 语言 | 理由 |
|---|---|---|
| 核心 daemon（调度 / SQLite / 检索 / HTTP+MCP / 权限） | **TS** | 变更快、单进程、热路径已达标 |
| 记忆流水线（抽取 / 归并 / 显著性 / 评估） | **Python 子进程** | 迟早要接 `transformers` / `datasets` / 评估工具；`markitdown` 已在 Python 里 |
| 文档转换 | Python（已装好） | `tools/ingest_pdfs.py` |

好处：两侧通过 **JSONL / stdin-stdout** 通信（与 inbox 同一个格式），任一侧重写都不影响另一侧。将来若要把流水线换成 Rust（性能需要），也只是换一个子进程。

**这条边界现在就要划清**，否则半年后流水线会长进 daemon 里，再也拆不开。

## 6. 什么情况下必须换（可执行判据）

| 触发条件 | 换成 | 成本 |

现在的实测数据（67 MB / 130 ms / 8.6 ms）**离任何一个触发点都还很远**。

## 7. 一句话

**我原来是用"生态"给语言找理由，那是倒过来的。** 正确的顺序是：先看变更在哪、瓶颈在哪、守护能不能被外部机制满足——三条都指向"要一门改得快、且不构成瓶颈的语言"。

TypeScript 仍然是答案，但它的**前置条件是补上 `tsc --noEmit`**；而**记忆流水线应当从今天起就留在 Python 子进程里**，因为那条边界一旦消失，就再也划不回来了。
